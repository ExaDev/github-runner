# github_runner_cluster

Runs a k3s cluster under Docker Compose on each host, from the `docker-compose.yml` and k3s image build context the role ships in `files/` and copies to `github_runner_cluster_dir` on the target host: embedded etcd across the server nodes (or SQLite for a single server), and a Tailscale client inside each node's k3s container (k3s `--vpn-auth`) so nodes on different networks can reach one another over a mesh. It templates that directory's `.env` and starts the `server` or `agent` Compose profile. The mesh's control server is pluggable: Tailscale's own, or Headscale in one of three arrangements (see [Mesh providers](#mesh-providers)).

Which hosts are servers is decided automatically from the inventory group named by `github_runner_cluster_group`, in inventory order. The first N hosts are servers, where N is the largest odd number no greater than both the number of hosts and `github_runner_cluster_max_servers`: 1 or 2 hosts give 1 server, 3 or 4 give 3, and 5 or more give 5. The first server bootstraps the cluster, the other servers join it, and the remaining hosts join it as agents. The group is used rather than the play's hosts so that `--limit` never changes the result. The logic lives in `tasks/topology.yml` and the collection's `exadev.github_runner.cluster_topology` filter (`plugins/filter/cluster_topology.py`), and publishes `github_runner_cluster_effective_node_role`, `github_runner_cluster_effective_bootstrap`, `github_runner_cluster_effective_server_url` and `github_runner_cluster_effective_tls_sans` for each host.

A host that sets `github_runner_cluster_node_mode: native` does not use Docker at all: it runs k3s directly under systemd, as an agent or, when its inventory says so, a server and etcd voter, with the host's own Tailscale client as the node's device on the mesh. See [Native nodes](#native-nodes), which also says what that gives up. Everything below that mentions a container, Compose or a Docker context is about the default mode, `compose`.

## Docker Compose versions

The role reads `docker compose version` first and fails, before changing anything on the host, if it is 2.37.1 or later but older than 2.39.0. Those releases create a container from an image they have just built without recording that image's ID on it ([docker/compose#13047](https://github.com/docker/compose/pull/13047)), so the next run sees a different image and recreates the container, which restarts every node on the run after the one that built the k3s image. Releases before 2.37.1 and from 2.39.0 on keep the containers. GitHub's ubuntu-latest runner image has shipped 2.38.2, so a CI job that runs the role there needs a different Compose installed first, as `.github/workflows/mesh-integration.yml` does.

## Versions

Every node's image is built from two pinned tags: `github_runner_cluster_k3s_version` (a `rancher/k3s` release tag, k3s's version with `+` written as `-`, such as `v1.34.1-k3s1`; release candidates are not accepted) and `github_runner_cluster_tailscale_version` (a `tailscale/tailscale` tag such as `v1.102.4`). The defaults are the versions this collection's integration tests run. The role writes both into the host's `.env`, the Compose file refuses to build without them, and the Dockerfile has no default for either, so no node is ever built from `latest`. Set them once for the whole group, in the inventory or `group_vars`, not per host and not in play vars.

Before it changes anything on a host the role fails:

- if either is not a pinned tag;
- if the hosts of `github_runner_cluster_group` do not all name the same k3s minor version, listing each host's version. Every host is read from the inventory, and one that sets nothing counts as the default, so the check gives the same answer on every host, including under `--limit`;
- if the k3s version would break k3s's upgrade path or Kubernetes' version skew policy from what runs now. k3s cannot be downgraded and upgrades the cluster one minor at a time, servers before agents; the [version skew policy](https://kubernetes.io/releases/version-skew-policy/) ([archived](http://web.archive.org/web/2026/https://kubernetes.io/releases/version-skew-policy/)) keeps the API servers within one minor of each other and never lets a kubelet be newer than an API server, while older kubelets are supported. So the role refuses to build this node older than it runs (by patch release and k3s build too), any node more than one minor above another, a server an older minor than any node runs, and an agent a newer minor than any server runs. Patch releases on other nodes are not compared. The agent rule applies only when the run builds the agent's image (it is missing, as for a new agent): changing the pin builds nothing, so writing a new pin to every host before the servers are rebuilt, as the upgrade below does, passes. The role reads `k3s --version` in this node's container, and the nodes' kubelet versions and roles through every server of the group in the inventory, each on its own host with its pinned Docker context, so one server stopped or being rebuilt does not hide what the others run. Each server's read, its Docker daemon and `docker exec` included, gets at most `github_runner_cluster_cluster_read_timeout` seconds, so one that hangs is cut off and named rather than holding up every host; the docker process it ran may stay on that host until the daemon answers. When servers run but none of them can be read, it refuses, naming each and why. When no server's container runs it compares only this node's own container and says why: a first bootstrap, a group that joins a cluster whose other servers are outside the inventory (as `bootstrap.sh` builds for a joining server), or a group whose inventory holds no server at all (a host `bootstrap.sh` joins as an agent). `-e github_runner_cluster_allow_k3s_version_jump=true` skips this comparison for one run: for a deliberate downgrade, a cluster that is being replaced, or one that cannot be read. Another server's container name and Docker context are read from its inventory (hostvars), so set them there, not in play vars.

A new cluster can start on a newer k3s than the default by setting both variables; the integration tests have run only the defaults.

### Upgrading from a release before the pins

Releases before the pins built every node from `latest`, and this change refuses what they accepted:

- `github_runner_cluster_k3s_version: latest`, or `K3S_VERSION=latest` in `.env.bootstrap`: set the `rancher/k3s` tag the cluster runs instead (`k3s --version` in a node's container, with `+` written as `-`), or leave it unset for the default;
- a cluster that floated to a newer k3s minor than the default: set `github_runner_cluster_k3s_version` to the tag it runs, once for the whole group, before running the role;
- a Compose file path (in `github_runner_cluster_dir` or `github_runner_cluster_compose_files`) with a colon in it: move it, since `.env` now lists the files in `COMPOSE_FILE`.

Set `github_runner_cluster_tailscale_version` too if the nodes run another Tailscale than the default (`tailscale version` in a node's container). The first run after upgrading rewrites each node's `.env` and recreates nothing.

Changing a pin changes no running node. Compose builds the image only when it is missing and leaves the build arguments out of a container's configuration hash, so the next run of the role rewrites `.env` and leaves the container alone. To move the cluster to a new version, run the role once with the new pins, so every host's `.env` names them, then rebuild and restart the nodes by hand, one at a time.

The node's `.env` names the Compose files, as absolute paths, and the project the role runs the node with (`COMPOSE_FILE` and `COMPOSE_PROJECT_NAME`), so a `docker compose` command run by hand in `github_runner_cluster_dir`, or with `--project-directory` pointing at it, acts on the same project with the same files, including the extra file a `headscale_in_cluster` bootstrap server or a `github_runner_cluster_compose_files` entry adds. Each command still needs `--profile server` (or `--profile agent` on an agent), since every service sits in a profile, and, on a host with `github_runner_cluster_docker_context` set, that context: run it as `docker --context <context> compose ...`.

1. Read k3s's release notes for every minor version between the old and the new one. A jump of more than one minor is several upgrades, each run to the end before the next, and the role refuses to build a node more than one minor ahead of the cluster.
2. Servers first, one at a time. Servers run runner pods as well as the control plane, so before each one:
   - check that every server's node is Ready (`kubectl get nodes`) and that each server's own API reports etcd healthy (`kubectl get --raw '/readyz?verbose'` through that server lists `[+]etcd ok`), so the cluster keeps its quorum while this one restarts: with three servers, at most one may be down;
   - cordon it (`kubectl cordon <node>`) and wait until no runner pod is left on it (`kubectl get pods --all-namespaces --field-selector spec.nodeName=<node>`), so no job is cut off, then drain the rest (`kubectl drain <node> --ignore-daemonsets --delete-emptydir-data`).

   Then, in `github_runner_cluster_dir`, run `docker compose --profile server build k3s` and `docker compose --profile server up -d k3s`. Wait until its node is Ready again and the etcd checks above pass on every server, then `kubectl uncordon <node>`, before the next server.
3. Then agents, one at a time, the same way: cordon, wait for its runner pods to finish, drain, `docker compose --profile agent build k3s-agent` and `docker compose --profile agent up -d k3s-agent`, wait for Ready, uncordon.

A Tailscale upgrade on its own follows the same order; it restarts each node's mesh client with the node.

The role copies the new `docker-compose.yml` before it writes `.env`. A run that stops between the two (a failed check, a lost connection) leaves a Compose file that needs `TAILSCALE_VERSION` beside an `.env` without it, and every hand-run `docker compose` command in that directory fails with a missing-variable error until a run of the role succeeds.

## Node passwords and recreating servers

k3s keeps a node's password in `/etc/rancher/node/password`, and the cluster holds a Secret for it (`kube-system/<node>.node-password.k3s`). A container with a fresh filesystem generates a new password, the cluster rejects it ("Node password rejected" in the node's log) and the node stays `NotReady`. Compose recreates a container whenever its rendered configuration differs from the one it was made with, so every node service mounts a named volume at `/etc/rancher/node` (`<project>_k3s-node` on a server, `<project>_k3s-agent-node` on an agent), and the password outlives the container.

### Cutover for an existing node

A node made before the volume existed keeps its identity if the volume is seeded from its running container before Compose recreates it with the volume mounted, and the role does that on its own:

- Before the mesh step and every Compose task, the role looks for the node's volume. When it does not exist and the node's container does (running or stopped), the role creates the volume with the labels Compose gives its own volumes and copies `/etc/rancher/node` from the container into it. The copy is one `docker cp` piped into another, into a throwaway container made from the node's own image and never started, so the password is on no disk of the host, in no command line and in no output, and the volume keeps its mode and owner. A failed copy removes the volume again and fails the run, so the next run tries again. A host with no container yet, or with the volume already, is left alone, and a second run changes nothing. With `--check` the role only reports that it would seed.
- The Compose file now mounts the volume, which changes the configuration hash of the node's service, so the run that follows recreates each node's container once, with the password in place and the node rejoining as itself. That restarts k3s and the pods on that node: on a cluster whose jobs must not be cut off, run the first converge host by host with `--limit`, draining each node first as in [Versions](#versions). Servers are recreated one at a time whatever the play (see below). Agents are not held to that, so limit a cutover run to a few agents at a time if the cluster cannot lose them together.
- Under `--check` the cutover run reports the seeding. The recreates it will cause are not visible yet, since `--check` writes nothing and the check reads the files already on the host: they show under `--check` once the Compose file that mounts the volume has been copied to the host.

The volume is named from the Compose project, so changing `github_runner_cluster_compose_project` on a running host starts a new, empty volume as it does a new, empty node.

### Recreating servers one at a time

Compose recreates a container when the hash it stored on it (the `com.docker.compose.config-hash` label) differs from the hash of the configuration it renders now. Before it starts a server, the role makes the same comparison, between the container's label and `docker compose config --hash '*'` for the files and `.env` on the host:

- With `--check`, a server that would be recreated is reported as a change, with the reason (the two hashes, shortened). A hash is read from the files already on the host, so a difference that only this run's own copy of the Compose file or `.env` would create is visible once they are written, not under `--check`. A Compose file the role would add to a host that has run it before, such as `docker-compose.node-labels.yml` for a host that turns the role controller on, is not there under `--check`, so every Compose command and the Compose modules are given only the files the host has (`github_runner_cluster_compose_files_in_use`), a server that would gain a file is reported as recreated by name, and a Compose file of your own that is missing is still an error. In a real run the role writes its files first and names all of them.
- A running server is recreated only while every other server reports Ready, read through the server's own container. Recreating it stops its etcd member, and the cluster must keep its quorum meanwhile. When another server is not Ready, is not registered or cannot be read, the run fails for that host with the server named and nothing changed, under `--check` too. While none of the other servers is registered yet (the bootstrap server of a cluster that is still being brought up, restarted before anything has joined it) there is no quorum to keep, so that recreate goes ahead and is not waited for. To recreate a server anyway when the others cannot come back, run `docker compose up -d` for it by hand, as in the upgrade steps under [Versions](#versions). A server whose container is stopped is not a member of the quorum, so it is recreated without the check. Agents are exempt from it.
- The servers take turns, one at a time and in no fixed order: each turn checks, starts the server and, when it recreated a running container, waits for that server's node to report Ready on a heartbeat from the new container, meaning its lease (`kube-node-lease/<node>`) was renewed after the container started, since the API keeps the old container's Ready condition for a while (for as long as `github_runner_cluster_server_ready_timeout` allows) before the next server's turn begins, so no two servers are ever away together and a server that does not return stops the run with the others untouched. This relies on Ansible's linear strategy, the default; under `strategy: free` hosts do not wait for each other and nothing keeps the turns apart.

### A replaced node

The manual Secret deletion is for a node that is genuinely new under an old name: a host replaced with the same node name, or a node whose volume was removed (`docker compose down -v`, `docker volume rm`). Its new container generates a password the cluster does not know. Fix: on the bootstrap host, `kubectl delete secret <node>.node-password.k3s -n kube-system` (and, for an agent, `kubectl delete node <node>`), then restart the container. With `github_runner_cluster_wait_for_nodes` the role does this itself for a non-bootstrap host whose node is missing or not Ready after the run. Never delete a server's Node object: k3s then removes its etcd member, which cannot rejoin until its local datastore is moved aside.

## Native nodes

`github_runner_cluster_node_mode: native` in a host's `host_vars` runs that host's k3s node directly on the host, as the systemd service `k3s-agent` (an agent) or `k3s` (a server), with no Docker or Compose layer. The default, `compose`, is everything else in this README. A node under Compose nests containerd inside a container, so every image layer is overlayfs on overlayfs and pod egress goes through the container's NAT as well; a native node's containerd uses the host's filesystem and network. It is for a Linux host that systemd runs. A native host is a server only when it asks to be: `github_runner_cluster_node_role: server`, or `github_runner_cluster_bootstrap: true` to bootstrap the cluster. `tasks/topology.yml` never gives it a server place automatically and does not count it towards the automatic server number, so an inventory whose native hosts set neither keeps all of them agents whatever `github_runner_cluster_max_servers` allows; the server count with them must still be odd. See [Native servers](#native-servers). It also refuses a native host that sets `github_runner_cluster_network_mode: host`, since that setting puts a Docker node's container on the Docker host's network and a native node has no container (it already runs on the host's own network, with the host's own Tailscale client). Add the host to the cluster group like any other (its place in the group does not matter, since it never takes an automatic server place), set `github_runner_cluster_node_mode: native` and `github_runner_cluster_tailnet_domain` for it, and run the playbook with `--limit` to it. A play runs a native host's tasks before any Docker host's (the role's first task includes them, and Ansible's linear strategy runs an include for the hosts that take it while the others wait), so a native node never waits on a Docker server the same run is still to start: bring the servers it joins up first, in a run of their own. Its tasks that change the host use `become` on their own, so the connecting user needs passwordless sudo or `--ask-become-pass`. `examples/native-agent/inventory.yml` is a starting point, and `examples/native-server/inventory.yml` for a native server and a standby. The kernel modules and sysctls k3s needs are set by `github_runner_cluster_k3s_prerequisites` (see [Host preparation](#host-preparation)); k3s loads the modules and sets most of the sysctls itself when it starts, so the node does not depend on it. The rest of what a host dedicated to the cluster needs (not suspending, a quiet Wi-Fi radio, a headless boot, security updates that never reboot it) is the operator's to provide before the play runs, as the Prerequisites section of the repository README says.

The role reads the same secrets and settings as the Docker path and joins the same cluster: `github_runner_cluster_k3s_token`, the mesh's join key and control server (`tasks/mesh/main.yml`, whichever provider is in use), the node name rules (`github_runner_cluster_node_name`, else the inventory name), the API port (`github_runner_cluster_api_port`, checked to be one port for the whole group by the same `tasks/api_port.yml`), the join URL `tasks/topology.yml` works out, `github_runner_cluster_node_taints` (written as `node-taint` in k3s's configuration, so they are applied each time the node registers, as they are under Compose), and the pins `github_runner_cluster_k3s_version` and `github_runner_cluster_tailscale_version`. Node labels are not set by this role under either mode: the ARC role labels nodes by name from the API (`github_runner_arc_labelled_nodes`), so a native node gets its labels the same way.

A run does this, in order, and every step is idempotent and honours `--check`:

1. Checks the host (Linux, systemd, an architecture k3s publishes a binary for, Debian or Ubuntu if the role installs Tailscale), the topology, the pins, the API port, the token and the mesh, before anything is changed.
2. Compares the k3s version it is to install with the installed binary and with every node as the servers report it, with the same upgrade path and version skew rules as the Docker path (see [Versions](#versions)), reading the cluster through every server of the inventory and every host marked eligible (a Docker server's container, a native server's `k3s kubectl`). Each node's role in those rules is its live `control-plane` label, this node's included, so a host whose role changed at run time is held to the rules of the role it runs. `github_runner_cluster_allow_k3s_version_jump` skips it.
3. Decides the role the host runs (below), and for a server whether it bootstraps a new cluster or joins one. Then installs the pinned Tailscale package, adding Tailscale's apt repository when the host has none, and keeps its service running; then checks which tailnet the client is logged in to (below).
4. Downloads the k3s release binary `github_runner_cluster_k3s_version` names (the image tag's `-k3s` written `+k3s`, as GitHub names the release) to `/usr/local/bin/k3s`, checked against the SHA-256 the same release lists for the host's architecture or `github_runner_cluster_native_k3s_sha256`. The file is replaced in one rename, so a running k3s keeps its old binary until it restarts.
5. Writes `/etc/rancher/k3s/agent.yaml` (server URL, node name, taints, the kubelet's resolver file), on a server or a host marked eligible `/etc/rancher/k3s/server.yaml` and its drop-in `server.yaml.d/10-join.yaml` (below), the node's token and `--vpn-auth` value as two files of their own (mode 0600, written by tasks that log nothing, so the configurations name the files and hold no secret), the helper scripts under `/usr/local/lib/github-runner-k3s/`, both units `/etc/systemd/system/k3s-agent.service` and `k3s.service`, and the role file `/var/lib/rancher/k3s/fleet-role` when the host has none. Earlier releases wrote the agent's flags to `/etc/rancher/k3s/config.yaml`, which is removed, since each unit passes its own file as `--config`.
6. Runs the unit of the host's role: enables and starts it, restarts a running one when its binary, configuration, secrets or unit changed (pods keep running, because the units' `KillMode=process` leaves their containerd shims alone), or switches the host between its units when its role changed. A restart that is refused or fails is not lost: a marker beside the role file (`fleet-restart-pending-<unit>`) says the unit's files changed since it last started, and the next run restarts it. Then it checks the node: the unit of the role is active and the other is not, the host's Tailscale client is on the cluster's tailnet, and a server sees the node Ready on a heartbeat later than the start (the same rule as a recreated server's, `tasks/server_ready.yml`), and for a server also a voting member of etcd. A cluster whose servers are outside the inventory has no server to ask, and the run says so.

`github_runner_cluster_native_start: false` stops after step 5 and leaves the units as it finds them (a first install stays disabled and stopped, and a host whose role is to change keeps running its old unit), which stages a host before it joins or before its role is switched.

### Native servers

A native server is configured as every Docker server is, because k3s refuses a server whose critical configuration differs from the cluster's (`critical configuration value mismatch between servers`, `pkg/cluster/bootstrap.go`; the fields are `CriticalControlArgs` in `pkg/daemons/config/types.go` at [v1.34.1+k3s1](https://github.com/k3s-io/k3s/blob/v1.34.1%2Bk3s1/pkg/daemons/config/types.go)): `server.yaml` disables traefik and the network policy controller, leaves the cluster and service networks at k3s's own, names every server and every eligible host as a TLS SAN, passes `github_runner_cluster_etcd_heartbeat_interval` and `github_runner_cluster_etcd_election_timeout` as `etcd-arg` (checked by the same `tasks/etcd_timing.yml`, so the servers agree), and `https-listen-port` when `github_runner_cluster_api_port` is not k3s's own. The admin kubeconfig is root's alone (`write-kubeconfig-mode: "0600"`), and the role reads the cluster through it with `k3s kubectl` under `become`.

**etcd's peer address is the host's Tailscale address.** k3s builds etcd's peer URL from its private IP, which it takes from `--node-ip` before the `--vpn-auth` integration sets only the advertise address (`pkg/cli/server/server.go`: "Etcd IP (PrivateIP) remains the local IP"), so without it a native server's etcd would advertise a LAN address and lose its peers whenever the host changes network. The server unit runs `files/native/write-node-ip.sh` before every start, which writes `node-ip` into `server.yaml.d/00-node-ip.yaml` from the client's own address (logging the client in first with exactly the `tailscale up` k3s runs, from the same `--vpn-auth` file, when it has none yet). k3s reads `server.yaml`, then every `*.yaml` in `server.yaml.d` in name order (`dotDFiles` in `pkg/configfilearg/parser.go`).

**Two units, one role.** Both units are written on every native host, and each starts only while the role file `/var/lib/rancher/k3s/fleet-role` names its role: each unit's `ExecCondition` runs `files/native/fleet-role-is.sh`, and systemd skips a start whose condition exits 1 to 254 without marking the unit failed, and `Restart=always` never restarts a unit whose start was skipped that way (`service_shall_restart` in systemd's `src/core/service.c`), so the two never run together and a demoted server is never started again by its own restart policy. The server unit's condition also refuses while k3s's datastore holds a tombstone (`server/db/etcd/tombstone`, which k3s writes when its etcd member is removed and would otherwise act on at its next start by joining again as a new learner), so a server whose member was removed while its role file still named it a server, because it was down at the time, does not rejoin; moving `server/db` aside, as a demotion does, takes the tombstone with it (see [The role directory and a former member](#the-role-directory-and-a-former-member)). A host set up before the role file existed runs the agent unit and is recorded as an agent. For a host marked `github_runner_cluster_voter_eligible` the inventory gives only the role it starts with; once its role file names a role, a run keeps it, since the controller that moves votes changes it at run time. For any other native host the inventory decides, and a run whose inventory role differs from the role file switches the host.

**Bootstrapping, joining and rejoining.** `server.yaml.d/10-join.yaml` holds `cluster-init: true` only when the host is the inventory's bootstrap host, has no datastore (`server/db`) and none a demotion moved aside (`server/db.demoted`), and no other server of the inventory (Docker or native, or eligible) answers as running one; a server that cannot be read refuses the run, since starting a second cluster beside the real one would split the fleet. Otherwise it holds `server:`, the bootstrap host's join URL, or for the bootstrap host itself the first other server that answered, so a host that was ever a member, or a bootstrap host that comes back after the cluster moved on, always joins the cluster that exists. k3s joins a new server as an etcd learner and the leader promotes it once it has caught up (`MemberAddAsLearner` in `pkg/etcd/etcd.go`), so a learner never costs quorum, and the turn ends only once the node's `EtcdIsVoter` condition is True. A native bootstrap host is refused under `headscale_in_cluster`, whose bootstrap server runs Headscale as a static pod under a supervisor only the Docker node has (`files/k3s/node-entrypoint.sh`).

**The restart guard.** Native servers take turns, one at a time, as recreated Docker servers do ([Recreating servers one at a time](#recreating-servers-one-at-a-time)). A restart, a first start beside an existing cluster, or a promotion goes ahead only while every other etcd voter is Ready, the voters being read from each node's `node-role.kubernetes.io/etcd` label as the cluster reports it now, never from the inventory. Under `--check` the guard still reads and refuses, and the change is reported, not made.

**Switching role.** The node keeps its name, its node password (`/etc/rancher/node/password`, which neither unit is told to change) and its Tailscale device. Both directions cordon the node, wait up to `github_runner_cluster_native_runner_wait_timeout` seconds for its ARC runner pods to finish, and drain it; a node that cannot be emptied is uncordoned and the run fails with the units as they were, so a planned switch never cuts a job. A promotion then writes `server` to the role file, stops and disables the agent unit and starts the server unit, through the role actuator's host-local promotion (`fleet-role-actuator promote-local`, see [Role actuator](#role-actuator)), so that the role and the controller's swaps switch a host one way. A demotion is make-before-break: it goes ahead only while at least `github_runner_cluster_native_demotion_min_voters` (3) other voters, every one Ready, remain, so the cluster gains a voter before it loses one (etcd calls a two-member cluster unsafe). It writes `agent` to the role file first, so that neither `Restart=always` nor a reboot can start the server again (k3s marks a removed member's datastore with a tombstone and would rejoin it as a learner), then removes the etcd member through k3s's own controller (`etcd.k3s.cattle.io/remove=true` on the Node through another server, waiting for k3s to record `etcd.k3s.cattle.io/removed-node-name`; `pkg/etcd/member_controller.go`), then, through the role actuator's host-local demotion (`fleet-role-actuator demote-local`), stops and disables the server unit, forgets its regrading level, moves `server/db` aside to `server/db.demoted` (replacing an older copy, and keeping the snapshots in it), because k3s reuses any datastore it finds and would start the old member again on a later promotion, and starts the agent unit, and then takes the server role labels and k3s's etcd annotations off the Node, which the agent's k3s puts none of back. Moving votes between hosts on its own is not this role's: it only makes a switch safe when the inventory or the role file asks for one.

**Firewall.** The role opens nothing. Every peer reaches a native server over `tailscale0`; a host whose firewall limits the API (`github_runner_cluster_api_port`), etcd (2379 and 2380) and kubelet (10250) ports to `tailscale0` and loopback keeps them off the LAN.

### Tailscale

Each Docker node runs its own Tailscale client inside its container, so it neither depends on nor collides with the host's. A native node has no container, so the choice is whose Tailscale client k3s's `--vpn-auth` uses, and the decision is: **the host's own client is the node's, the host is dedicated to the cluster, and a client logged in to another tailnet is logged out of it first.** k3s's `--vpn-auth` runs `tailscale up --authkey <join key> --timeout=30s --reset` (adding `--login-server` for Headscale), and then reads the node's address from `tailscale status --json` and its flannel interface from the interface `tailscale0` (`pkg/vpn/vpn.go` in the k3s repository, [v1.34.1+k3s1](https://github.com/k3s-io/k3s/blob/v1.34.1%2Bk3s1/pkg/vpn/vpn.go) ([archived](http://web.archive.org/web/2026/https://github.com/k3s-io/k3s/blob/v1.34.1%2Bk3s1/pkg/vpn/vpn.go)); the integration is documented at [Distributed hybrid or multicloud cluster](https://docs.k3s.io/networking/distributed-multicloud) ([archived](http://web.archive.org/web/2026/https://docs.k3s.io/networking/distributed-multicloud))). The role installs the pinned client and keeps it running; the login itself is k3s's, with the join key, as the service starts. It adds Tailscale's apt repository only when the host has none, and leaves a repository file it finds as it is, so after a distribution release upgrade (which disables third-party repositories) remove `/etc/apt/sources.list.d/tailscale.list` and its signing key if the pin is to change, and the next run adds the new release's.

The options, each measured or read from the source, on an Ubuntu host that already ran its own client:

- **A second `tailscaled` on its own socket, state directory and interface: no.** k3s runs `tailscale` from `PATH` with no `--socket`, and `--socket` is a flag of the `tailscale` command and not of `up` (`rootfs.Func("socket", ...)` in `cmd/tailscale/cli/cli.go`), so k3s's `extraArgs` cannot carry it; a `PATH` wrapper that adds it works, which is how the container nodes wait for the join host (`files/native/tailscale-up-wait.sh`). The interface is the blocker: k3s looks up `tailscale0` by name, so the second client needs that name, and the host's already has it (`TUN device tailscale0 is busy ... device or resource busy`, measured with Tailscale 1.84.0). Renaming the host's would move the problem, and two kernel-mode clients also rewrite each other's netfilter chains: starting the second one removed all of the first's `ts-input` and `ts-forward` rules in the measurement, while a user-space second client (`--tun=userspace-networking`) touched nothing, and has no interface for flannel.
- **`--vpn-auth` pointed at another socket through the environment: no.** The `tailscale` command reads no environment variable for its socket (`TS_SOCKET=<second socket> tailscale status` still answered from the host's client, measured), so it is the wrapper again, with the same interface name problem.
- **Only the Tailscale client in a container or network namespace, k3s native: no.** k3s has to see `tailscale0` and run `tailscale` in its own network namespace, so putting the client elsewhere puts k3s there too, which is the nested network path this mode removes.
- **Another transport: no.** Whether a node uses flannel's `tailscale` backend is decided by its own `--vpn-auth` (`nodeConfig.FlannelBackend = vpnInfo.ProviderName` in `pkg/agent/config/config.go`), and the other nodes reach its pods over Tailscale subnet routes, so a node joined some other way would run another backend and its pods would be unreachable. Headscale is a control server the same client registers with (`github_runner_cluster_mesh`), not another transport.
- **The host's own client, dedicated to the cluster: yes.** One client, one interface, one set of firewall chains, and the one k3s's code is written for. What it costs is that the host cannot also be a member of another tailnet.

Because the client is the host's, the role guards against the cases where `tailscale up --authkey` would not do what the join needs. It never logs the client in itself. A client logged in to another tailnet makes the run stop, naming both tailnets, because `tailscale up` with a key does not move a logged-in client to the key's tailnet, and k3s from v1.35.0 skips `tailscale up` altogether while the client is running (`StartVPN` in [v1.35.0+k3s1](https://github.com/k3s-io/k3s/blob/v1.35.0%2Bk3s1/pkg/vpn/vpn.go) ([archived](http://web.archive.org/web/2026/https://github.com/k3s-io/k3s/blob/v1.35.0%2Bk3s1/pkg/vpn/vpn.go)); v1.34.1 runs it on every start). `github_runner_cluster_native_tailscale_leave_other_tailnet: true` has the role run `tailscale logout` first, which takes the host off that tailnet and cuts anything that reaches it over that tailnet, an SSH session included, so the inventory must reach the host another way (a LAN name) before it is set. The end check reads the client's tailnet again once k3s has started and fails unless it is the cluster's, so a node that joined the wrong tailnet is never reported as up. The tailnet is told apart by `github_runner_cluster_tailnet_domain`, which a native host must therefore have set.

### DNS

The container nodes point the kubelet at a resolver file naming only Tailscale's resolver, `100.100.100.100`, which forwards every other name to the container's original servers. On a host with systemd-resolved the client cannot read the host's servers to forward to (`GetBaseConfig` in `net/dns/resolved.go` of the Tailscale source returns `ErrGetBaseConfigNotSupported`), so it answers only the tailnet's names and whatever global nameservers the tailnet's DNS settings name. Pods resolve through CoreDNS, which forwards to the servers in the kubelet's resolver file, so a file naming only `100.100.100.100` could leave every pod without public DNS. The service therefore writes the file before each start (`files/native/write-resolv-conf.sh`) from the host's own upstream servers, left without Tailscale's resolvers, loopback addresses and search domains. The cost is that pods on a native node cannot resolve tailnet names, which pods on a Docker node can; a workload that needs one has to use the address.

### What a native node gives up

- **The Compose project.** There is no `docker-compose.yml`, `.env`, build context, `docker-prune` service or Docker context for the node, no `github_runner_cluster_dir` and no recreate. systemd restarts the process (`Restart=always`), the role restarts it when something it reads changed, and the host's own logs are `journalctl -u k3s-agent` or `journalctl -u k3s`.
- **The image pin.** The k3s binary is pinned in its place. A Docker node ignores a changed pin until its image is rebuilt by hand; a native node's binary is replaced by the next run and the service restarted, after the version check has allowed it. Upgrade as for any agent: servers first, one minor at a time (see [Versions](#versions)), and cordon and drain the node first if its runner pods must not see the restart (they survive it, but the kubelet restarts).
- **The node password volume.** k3s keeps the node's password in `/etc/rancher/node/password` on the host, which the role never reads, writes or deletes, so it survives restarts, upgrades and reruns without anything like the seeding in [Node passwords and recreating servers](#node-passwords-and-recreating-servers). It is lost only if that file is removed or the host is reinstalled, and then the node is "a genuinely new node under an old name" ([A replaced node](#a-replaced-node)): `github_runner_cluster_wait_for_nodes` on a server host clears the stale Secret and Node object, or delete them by hand.
- **Removing a node.** Stopping a unit leaves the pods' containerd shims running. The role installs neither k3s's `k3s-killall.sh` nor its uninstall script (the installer writes them; see [Uninstalling](https://docs.k3s.io/installation/uninstall) ([archived](http://web.archive.org/web/2026/https://docs.k3s.io/installation/uninstall))). Drain the node, delete its Node object, then `systemctl disable --now k3s-agent k3s` and stop the shims. A server's etcd member is removed first, as for a demotion.
- **Tailnet names in pods** (above), and **a Docker-free host's `docker` tooling**: nothing in this mode runs `docker` on the host, so it need not be installed.

### A Wi-Fi-only host

A node on Wi-Fi drops off the network whenever the radio does, and it then flaps `NotReady`: the kubelet's heartbeat stops, the control plane marks the node unreachable, and the runner pods on it are evicted once the not-ready taint's toleration runs out, which fails the jobs they were running. The role cannot make Wi-Fi reliable, only stop it adding drops of its own: a radio in power-save mode sleeps between beacons and delays or drops packets. Turning power save off, and stopping a laptop suspending when its lid closes, which would take the node off the network altogether, are for the host's own configuration, before the play runs. A wired connection is better where there is one.

### Tests

`tests/unit/test_native_node.py` and `tests/unit/test_native_server.py` cover it without a real host: the filters in `plugins/filter/cluster_native.py`, the helper scripts, the defaults, argument specs and this README, and the role's tasks (`tests/native/run.yml`) against stand-ins (`tests/unit/native_stand_ins.py`) for `systemctl`, `tailscale`, `dpkg-query`, `apt-get`, `docker` and `kubectl` on `PATH`, a local server for the k3s release, and a server data directory laid out as k3s leaves it. For servers it checks a bootstrap with `cluster-init` and the Docker servers' flags, a join, the voter guard refusing a join and a restart (and the refused restart being made by the next run), a promotion in place, an abandoned promotion whose runner pods did not finish, a demotion refused while the member is a voter and made once it is removed, with the datastore moved aside and the identity kept, and a former member never starting a second cluster. `tests/mesh/run.sh native_server` runs a real native server as a privileged systemd container beside the Docker servers: it joins etcd as a learner, is promoted to a voter, and keeps the cluster writable throughout; then, with regrading turned on, its `fleet-regrade` unit steps it down to etcd-only and back up under simulated memory pressure, with its membership unchanged, its vote kept (a write succeeds with a Docker server stopped), the level kept across `systemctl restart k3s` and across the host stopping and starting, and no pod's shim left running at etcd-only. It checks a first run, idempotence, `--check`, a changed setting restarting the service once, a client in another tailnet (refused, then logged out first when allowed), a client k3s did not log in, a refused downgrade, a wrong sum, an unsupported host, the secrets staying out of the output, and the node's readiness as a server reports it.

## Host preparation

Two steps prepare a Linux host for k3s, in either node mode, and both are off by default. They run once per run, before the node is started or changed (a native node's after the role has installed the k3s binary), and are skipped on any other host. Their tasks that change the host use `become`. `tasks/host_prerequisites.yml` holds them.

- `github_runner_cluster_k3s_prerequisites` (default `false`): loads the kernel modules k3s needs (`overlay`, `br_netfilter`) and sets the sysctls it needs (`net.ipv4.ip_forward` and the two bridge-netfilter keys), each now and at boot, through a `modules-load.d` file and a `sysctl.d` file. A module is loaded only when `/sys/module` lacks it and a sysctl is set only when its value differs. Under `--check` each change is reported and none is made.
- `github_runner_cluster_containerd_apparmor_stacking_fix` (default `false`): installs and loads an AppArmor profile, `cri-containerd.apparmor.d`, that lets the processes of one container signal and trace each other under the stacked label Ubuntu 26.04 gives it (containerd/containerd issue 14485). It is off by default because it replaces a security profile and is needed only where the kernel stacks the label, which is a Ubuntu 26.04 native node. The profile is taken from one containerd release (`github_runner_cluster_containerd_apparmor_containerd_version`), so the step fails when the k3s on the host carries another, and it is compiled before it replaces the file, so a profile the parser rejects never reaches `/etc/apparmor.d`. A host without AppArmor enabled is left alone, with a message. `defaults/main.yml` has the whole reasoning.

The paths and lists the steps use (`github_runner_cluster_kernel_modules`, `github_runner_cluster_sysctl_settings`, `github_runner_cluster_modules_load_file`, `github_runner_cluster_sysctl_file`, `github_runner_cluster_sys_module_dir`, `github_runner_cluster_apparmor_enabled_file`, `github_runner_cluster_apparmor_profiles_file`, `github_runner_cluster_containerd_apparmor_profile_name`, `github_runner_cluster_containerd_apparmor_profile_file`, `github_runner_cluster_k3s_binary`) are constants, and variables only so the tests can point them at a stand-in.

## Docker host disk

Each host also runs a `docker-prune` service that removes Docker build cache and dangling images older than `DOCKER_PRUNE_AFTER` (a week by default) once every `DOCKER_PRUNE_INTERVAL_SECONDS` (daily). The node's ephemeral storage lives on the host's Docker disk, shared with anything else that builds there, so an untrimmed cache eventually puts the node under disk pressure and taints it unschedulable. Tagged images, containers and volumes are never touched. Set either variable in the host's `.env` to change them.

## Docker contexts

By default the role drives whichever Docker daemon the host's current Docker context points at (`docker context show`), or the one `DOCKER_HOST` names when that is set. That is right for a host with one Docker engine, but the current context is shared, mutable state that other software changes. The case that matters: a Mac that runs its node in Colima and also has Docker Desktop installed. Launching Docker Desktop switches the current context to `desktop-linux` without asking, so the next run of the role would find no node in Docker Desktop and build a second, empty k3s node there, alongside the real one in Colima, instead of managing it.

Set `github_runner_cluster_docker_context` in the host's variables to pin the context by name (`colima` in that example) on any host with more than one engine. Every `community.docker` module call in the role then passes it as `cli_context`, and every `docker` command the role runs (Compose, `exec`, `inspect`, `volume`, image pulls, and the commands in `playbooks/recover_in_cluster_mesh.yml` and `playbooks/promote_headscale_standby.yml`) runs with `DOCKER_CONTEXT` set to it, so the modules and the CLI always reach the same daemon. The role checks the pin before it touches the host and fails if the context does not exist there, or if `DOCKER_HOST` is also set, since the two would name the daemon in conflicting ways. It never creates a context and never changes the host's current context; `docker context show` on the host reads the same before and after a run. The Headscale tasks that act on another host (the `headscale_hosted` server and standby, and the promotion playbook) use that host's own value. Run `docker context show` on each host to see what it currently points at before choosing a value.

## Container runtime after a reboot (macOS)

On a Mac the container runtime is a Linux VM (Colima, or Docker Desktop) that stays stopped after a reboot until something starts it. The node's k3s container has `restart: unless-stopped`, so it comes back by itself once the runtime does, but a host whose runtime never starts never rejoins the cluster. With three servers, two such hosts leave the cluster without quorum and no runner pods anywhere. Only macOS hosts are affected by any of this: the role does nothing about the runtime on a Linux host, where Docker is a system service.

Which runtime a Mac runs is taken from the Docker context the role drives (see [Docker contexts](#docker-contexts)): `colima`, or `colima-<profile>` for another profile, is Colima, and `desktop-linux` is Docker Desktop. `github_runner_cluster_runtime` says so explicitly for a host whose context does not tell, for example one that uses `DOCKER_HOST`, and `github_runner_cluster_colima_profile` names the profile to start when the context does not.

**Colima.** With `github_runner_cluster_runtime_autostart` on (the default, which acts on Colima hosts only), the role starts the profile if it is stopped, with `colima start --profile <profile> --activate=false`, so the profile does not make its context the host's current one, and installs the launchd job that starts it again after a reboot. There are two kinds, chosen by `github_runner_cluster_runtime_autostart_at` (`login`, `boot` or `auto`, the default). `auto` is `boot` for the profile named by `github_runner_cluster_runtime_boot_profile` (default `node`, the profile the bridged k3s node runs in) and `login` for any other, such as a `default` profile a host keeps for other workloads. A profile has one kind at a time: installing either retires the other's property list, unloading it first, so the profile is not started twice.

**At login (an agent).** The role:

- installs a launchd agent, `com.exadev.github-runner.colima.<profile>`, as `~/Library/LaunchAgents/<label>.plist` of the user Ansible connects to, which runs the same command at every login with a `PATH` that names both Homebrew prefixes (`github_runner_cluster_runtime_path`), since launchd gives an agent only the system `PATH` and Colima starts `limactl` and `docker` from the one it has, and with the profile's `COLIMA_HOME` when the profile does not live in `~/.colima` (a profile of a bridged node, such as `colima-node` in `~/.colima-node`, which Colima would otherwise look for in `~/.colima` and start as a new VM there). The `COLIMA_HOME` is `github_runner_cluster_colima_home` when that is set, and otherwise the directory the profile's Docker context points at, read with `docker context inspect`, which needs no running VM; a context whose endpoint is not `<COLIMA_HOME>/<profile>/docker.sock` fails the run with a message asking for the variable. A host whose profile lives in `~/.colima` gets an agent with no `COLIMA_HOME`, exactly as before; and
- loads the agent into that user's login session. A user with no login session on the host (nobody has logged in at the console since the last boot) cannot have an agent loaded, so the role installs the file, says so, and leaves launchd to load it at the next login.

The role reads what it needs to tell a Mac from another host (the kernel name) and to name the agent (the connecting user's id and home directory) with minimal `setup` subsets of its own when the caller has not gathered them, so a play with `gather_facts: false` works. The role never uses `become` for this: a LaunchAgent belongs to the user whose login session loads it, and Colima's VM runs as that user. Changing a definition unloads the agent before loading the new one; a rerun with nothing changed touches neither the agent nor the VM, and `--check --diff` shows the property list that would be written. With the variable off, the role installs nothing and leaves an agent from an earlier run as it is.

A Mac still has to log in for the agent to run: a launch agent starts with the user's login session, not with the machine. A host whose profile is started by an agent, and that should recover from a reboot unattended, needs automatic login for that user (System Settings > Users & Groups), which FileVault prevents. The k3s node's profile does not depend on it:

**At boot (a daemon).** For the profile that runs the node the role installs a launchd daemon instead, `com.exadev.github-runner.colima.<profile>`, as `/Library/LaunchDaemons/<label>.plist`, owned by `root:wheel` with mode `0644` (launchd refuses a daemon property list that anyone else can write), and loads it into the `system` domain (`launchctl bootstrap system <plist>`). A daemon runs when the Mac starts, whether or not anyone has logged in, so the profile and the node's container come back after a power loss with the Mac sitting at the login window. The daemon runs the same command with the same `PATH` and `COLIMA_HOME` as the agent does, as the connecting user (`UserName`, which launchd honours only for a job loaded into the system domain, and ignores for an agent: `man launchd.plist` on a Mac), with that user's `HOME` set in its environment, because launchd.plist(5) does not promise one for a daemon and Colima and Lima are Go programs, whose `os.UserHomeDir` is `$HOME` on macOS. Its log is in the user's `~/Library/Logs`, as the agent's is. Writing the property list and loading it take root, so the role uses `become` for these tasks and nothing else in the runtime tasks: run the play with passwordless sudo for the connecting user (a sudoers entry for the connecting user grants it) or with `--ask-become-pass`. Colima's network helper (`socket_vmnet`) and its sudoers entry are the user's, installed the first time a profile with an address starts, and the daemon runs as the same user, so it needs nothing the agent did not.

A host that got the agent from release 2.19.0 moves over on its next run: the role unloads the node profile's agent from the user's login session when there is one, deletes its property list (also when nobody has logged in, so it cannot load at the next login and start the profile a second time) and loads the daemon. Unloading either kind does not stop the VM, which the job started detached, and loading one runs `colima start`, which does nothing to a running profile. A rerun with nothing changed makes no `launchctl` call that changes anything. With `github_runner_cluster_runtime_autostart` off the role installs, loads and removes none of this.

**Docker Desktop.** The role cannot start Docker Desktop. Turn on Settings > General > Start Docker Desktop when you sign in to your computer on each such host (https://docs.docker.com/desktop/settings-and-maintenance/settings/), and give it the same automatic login. If it is not running when the role runs, the run fails with that message.

**End checks.** On every macOS host the role checks, before anything reads the daemon and again after it has started the node's Compose project, that the runtime answers (`docker info` through the host's Docker context), and after starting the project that the node's k3s container (`github-runner-k3s`, or `github-runner-k3s-agent` on an agent) is running. A converge of a host that rebooted therefore repairs a stopped Colima or fails with a message that says what to do, and never reports success over a node that is not up. A `--check` run does not fail on a stopped runtime or container it has not started.

**Colima kernel.** On every Colima host, whether or not `github_runner_cluster_runtime_autostart` is on, once the VM answers (`tasks/colima_kernel.yml`), the role makes the VM's kernel pass bridged pod traffic through iptables, now and at every VM boot: it writes `/etc/modules-load.d/br_netfilter.conf` and `/etc/sysctl.d/90-github-runner-br-netfilter.conf` in the VM, runs `modprobe br_netfilter` when the VM has no `/proc/sys/net/bridge`, and sets `net.bridge.bridge-nf-call-iptables` and `net.bridge.bridge-nf-call-ip6tables` to 1 when they differ. Without the module a pod that talks to a Service whose only backend pod is on the same node gets no reply, because the Service's reverse NAT never applies to the bridged hairpin traffic; pods on other nodes keep working, so it stays latent until a single-backend Service such as CoreDNS lands on the node (the `br_netfilter` note under Non-obvious behaviour in the repository README has the symptoms). Everything runs in the VM through `colima ssh --profile <profile>`, as the VM's user with `sudo`, and no `become` on the host. A file is written only when its content differs, so a rerun changes nothing, and the module file takes the name the README's note told people to create by hand, so an existing one is replaced by the managed one. Under `--check` each change is reported and none is made, and nothing is read from a VM that a check run would only have started. Docker Desktop's VM is not reachable by the role and other runtimes are not touched.

**Colima VM size.** A Colima host can set its VM's memory in GiB and its number of CPUs, `github_runner_cluster_colima_memory_gib` and `github_runner_cluster_colima_cpus`, each a positive whole number; empty, the default, keeps what the profile has (`tasks/colima_size.yml`). Instead of a memory, a host can say what it must keep: `github_runner_cluster_colima_memory_reserved_gib`, the memory its other workloads need, and `github_runner_cluster_colima_memory_host_reserve_gib`, the memory kept for macOS itself (by default macOS's wired memory plus the resident memory of every process but the node VM's, measured on node hosts and rounded to a whole GiB). The VM then gets the host's memory (`ansible_facts['memtotal_mb']`) less both, rounded down to a whole GiB, but never less than the node floor: the guest's own use with no runner pod on it, `github_runner_cluster_colima_guest_baseline_gib`, plus one runner pod's memory limit, `github_runner_cluster_colima_runner_memory_limit_gib` (which the scale set's values set, so the cluster role is told it, and which a derivation requires), rounded up to a whole GiB. A derivation below the floor sizes the VM at the floor and prints a warning that the host keeps less than its reserves. A memory set explicitly wins over the derivation, but with a reserve set it must fit the same budget: a memory above the host's memory less both reserves fails the run, naming the host's memory and both reserves, before the VM is read or the node cordoned, so a workload whose reserve grows can never leave the VM larger than the host affords. With neither a memory nor a reserve the profile's memory is left as it is. A host whose runtime is not Colima ignores all of these, so they can be set for a group that mixes runtimes, and says so under `-v`, naming the values it skips. A value of the wrong kind, or a derivation without the runner's limit, fails the run before anything is read from the VM. The role reads the size of the VM Lima runs with `colima list --profile <profile> --json`, not the profile's configuration file, since `colima start` given a size while the profile runs writes it to the file and leaves the VM as it is ([`cmd/start.go`](https://github.com/abiosoft/colima/blob/v0.10.3/cmd/start.go)). A VM that already has every size set is left alone, so a rerun changes nothing. Otherwise the resize is a planned restart of the node, made one host at a time, each in its own turn, through the same quorum guard as moving a node between networks (`tasks/restart_guard.yml`): it refuses unless the other servers with a Ready node and a healthy etcd stay a majority of all servers; it takes the `fleet-regrade` Lease that regrading steps hold (`kube-system/fleet-regrade`, as `colima-resize/<node>`), refusing while another step holds it, so a resize never overlaps a regrade step or another resize in this run or any other; it cordons the node, waits for its runner pods to finish and drains it (the role switch's `tasks/native/drain.yml`), checks the cluster again, runs `colima stop --profile <profile>` and `colima start --profile <profile> --activate=false --memory <GiB> --cpus <n>` (the flags of the values set), waits for the node to be Ready on a heartbeat later than the stop and, on a server, an etcd voter, uncordons it and gives the Lease back. Colima writes the new size to the profile's configuration, so the launchd job's later starts keep it. The node's container comes back with the VM (`restart: unless-stopped`). A node whose container is not running takes nothing from the cluster, so its VM is only stopped and started. When a step fails the node is uncordoned again and the run fails, saying whether the VM was stopped, and the Lease is given back, or expires after `github_runner_cluster_colima_resize_lease_seconds` when the API that holds it does not answer. Under `--check` the host's memory, the sizes, the Lease and the cluster are read, a refusal fails as it would in a real run, and the resize is reported and not made.

This is the role's whole scope: it never moves a host between Colima and Docker Desktop.

## Mesh providers

`github_runner_cluster_mesh` picks the provider. Each one lives in `tasks/mesh/<provider>.yml` and publishes the same facts, so nothing else in the role depends on which is in use:

- `github_runner_cluster_mesh_join_key`: a reusable, pre-authorised join key that tags each node with `github_runner_cluster_mesh_tag`.
- `github_runner_cluster_mesh_control_server_url`: the `--vpn-auth` `controlServerURL`, empty for Tailscale's own control plane.
- `github_runner_cluster_mesh_vpn_auth`: the resulting `--vpn-auth` value (`name=tailscale,joinKey=<key>[,controlServerURL=<url>]`), which `k3s/node-entrypoint.sh` builds the same way from `.env`.
- `github_runner_cluster_mesh_policy`: the tailnet policy as the provider knows it.

`tasks/mesh/main.yml` includes the provider, then runs the checks every provider shares: `tasks/mesh/check_policy.yml` fails, printing the exact JSON to merge in, unless the policy defines the node tag in `tagOwners` and auto-approves `github_runner_cluster_pod_cidr` for it in `autoApprovers.routes` (each node advertises its slice of the pod CIDR as a subnet route for flannel, and an unapproved route leaves pod traffic between nodes silently going nowhere). The role never writes a policy it does not own.

| Provider | Control server | Policy | Join key |
| --- | --- | --- | --- |
| `tailscale` (default) | Tailscale's | With a Tailscale API token, the role adds the tag, route approval and pod grant to the tailnet ACL, leaving every other entry alone; without one, it leaves the ACL alone | Supplied, or created through the API when it will be kept (see [Join keys](#join-keys)) |
| `headscale_existing` | A Headscale server someone else runs | Read through the REST API and checked, never written | Supplied, or created through the API when missing, expired or within `github_runner_cluster_headscale_join_key_renew_days` of expiry, when it will be kept (see [Join keys](#join-keys)) |
| `headscale_hosted` | Headscale under Docker Compose on one host outside k3s | Role-owned (`github_runner_cluster_headscale_policy`) | Created through the API and kept on the Headscale host |
| `headscale_in_cluster` | Headscale as a static pod on the bootstrap server | Role-owned | Created through the API and kept on the bootstrap server |

For every Headscale provider, `github_runner_cluster_tailnet_domain` is Headscale's MagicDNS base domain, since node addresses are `<node name>.<domain>`; it must not be, or be a parent of, the Headscale URL's own host name. The Headscale API is reached from the control node at `github_runner_cluster_headscale_api_url`, or the URL itself.

### headscale_existing

Needs `github_runner_cluster_headscale_url` and an API key (`headscale apikeys create --expiration 90d`) in `github_runner_cluster_headscale_api_key`. If the server's policy lacks the tag or the route approval, the run stops before creating anything and prints what to add.

### Join keys

Neither Tailscale nor Headscale lets a join key be read back after it is created, so the `tailscale` and `headscale_existing` providers create one only when it will be kept for the next run. The new key is set as the fact `github_runner_cluster_new_join_key` (`{mesh: tailscale or headscale, key: ...}`) and kept in either or both of two ways:

- `github_runner_cluster_join_key_path`: a file on the control node. The role writes a new key there (mode 0600) and reads the key from it whenever `github_runner_cluster_tailscale_join_key` or `github_runner_cluster_headscale_join_key` is empty.
- `github_runner_cluster_join_key_listener: true`: a secrets adapter in the play keeps it. The role notifies `github_runner_cluster join key created` and flushes handlers at once, so the key is stored even if a later task fails. The 1Password adapter does this and writes the key to its item.

With neither set, the role creates nothing, and a run with no join key stops asking for one to be supplied or for somewhere to keep a new one.

### headscale_hosted

Runs `headscale/headscale` at `github_runner_cluster_headscale_version` (pinned) under Compose on `github_runner_cluster_headscale_host`, by default the bootstrap server but any inventory host, including one outside the cluster group. Its files live in `github_runner_cluster_headscale_dir` on that host: `config/`, the Compose project, and `secrets/` (mode 0700) holding the API key it creates with Headscale's own CLI and the join key. `github_runner_cluster_headscale_tls: letsencrypt` (the default) has Headscale obtain its certificate itself over TLS-ALPN-01 on port 443; `none` serves plain HTTP on `github_runner_cluster_headscale_port`, for a TLS-terminating proxy or a private network. `github_runner_cluster_headscale_derp: embedded` adds Headscale's own DERP relay (STUN on UDP 3478) to Tailscale's public DERP map.

#### Backups and a warm standby

Headscale has no high availability of its own: one server, on SQLite. While it is down, tunnels that already exist keep working, but nothing can join, no key can be created, and route or endpoint changes stop reaching nodes. Setting `github_runner_cluster_headscale_litestream_replica` adds [Litestream](https://litestream.io) to the Compose project, pinned at `github_runner_cluster_headscale_litestream_version`. A `litestream-restore` step runs before Headscale on every start and restores the database from the replica when the host has none, then a `litestream` sidecar streams every change to the replica. The replica is Litestream's own replica block, so anything Litestream supports works: S3 or an S3-compatible store, SFTP to another host, or a file path on mounted storage (`github_runner_cluster_headscale_litestream_mounts`). Credentials go in `github_runner_cluster_headscale_litestream_env` and extra files such as an SFTP key in `github_runner_cluster_headscale_litestream_files`. Both are written to `litestream/` on the Headscale host with mode 0600, never into the Compose file. With Litestream on, Headscale's `wal_autocheckpoint` is 0, as Litestream recommends, so Litestream does the checkpointing itself.

The database does not hold Headscale's Noise private key, which identifies the server to every node. The role keeps a copy in `keys/` beside the configuration and the restore step puts it in place, so a server restored on the same host, or promoted from the standby, is the same server to its nodes. To rebuild on a new host with no standby, supply the key as `github_runner_cluster_headscale_noise_private_key` from wherever you keep secrets. A run fails, rather than changing the key, if it does not match the running server's.

`github_runner_cluster_headscale_standby_host` adds a warm standby on another inventory host. It gets the same configuration, keys, API key and join key, and a Compose project in which only `litestream-follow` runs, keeping a separate copy of the database up to date from the replica (`litestream restore -f`). Headscale, its restore step and its sidecar sit in the `active` profile and stay stopped. `playbooks/promote_headscale_standby.yml` promotes it. It stops Headscale and then its sidecar on the old server, so the sidecar copies the last writes as it stops. If the old server cannot be reached it refuses to go on unless `-e github_runner_cluster_headscale_promote_without_stopping=true` says that server is down, since two servers writing to one replica would each overwrite the other's history. It then restores the replica's latest state on the standby, replacing the follower's copy, and fails rather than start an empty server if the replica has nothing. Finally it starts Headscale and its sidecar there and prints the DNS change to make and the inventory change for the next `site.yml` run (`github_runner_cluster_headscale_host` becomes the standby). It changes neither. A host that was down when it was promoted away from restarts its containers when it comes back, because they were running when it went down, so stop its project (`docker compose stop` in its Headscale directory) before anything else.

What to expect:

| Setup | Data loss (RPO) | Recovery time (RTO) |
| --- | --- | --- |
| No Litestream | Everything since the last copy you made yourself; all of it if the host is lost | Rebuilding the host, then every node registering again |
| Litestream, no standby | Up to Litestream's sync interval (1 second by default), plus anything written while the replica was unreachable | Provisioning a host and running `site.yml`: the restore step brings the database back before Headscale starts |
| Litestream and a warm standby | The same | Running the promotion playbook (seconds to a minute, dominated by the restore), plus the DNS record's TTL, plus each node's next control reconnection attempt |

Nodes find the promoted server only through DNS, so keep the Headscale name's TTL short (60 seconds or so) where you use a standby. They reconnect by themselves once the name resolves to it. `tests/litestream/run.sh` measures the whole failover against a real Tailscale client. That client pins itself to HTTPS on port 443 after its first failed control connection, so a server behind `github_runner_cluster_headscale_tls: none` needs a TLS-terminating proxy on port 443 for its nodes to come back after an outage. Plain HTTP on another port is not enough.

### headscale_in_cluster

Runs Headscale inside the cluster it serves, as a static pod with host networking on the bootstrap server, published on that host's port. A static pod rather than a Deployment behind a LoadBalancer Service, because kubelet runs a static pod with no API server and no pod network, both of which here depend on the mesh. The bootstrap server's `k3s/node-entrypoint.sh` supervises k3s rather than exec'ing it: every time the container starts, k3s starts off the mesh (no `--vpn-auth`, and on SQLite until the cluster first reaches the mesh), kubelet starts Headscale, and once Headscale answers the script restarts only the k3s process on the mesh, with `--cluster-init` converting the datastore to etcd with the mesh address as etcd's peer address. Pods, Headscale included, keep running across that restart. On the first run the join key does not exist yet, so the role starts the bootstrap server, waits for Headscale, creates the keys, and only then starts the other nodes.

The limitation: the control server lives on one node. While the bootstrap server is down, nodes already on the mesh keep talking to each other, but nothing can join or re-register. A single-server cluster recovers from any restart on its own. With several servers, starting off the mesh leaves the bootstrap server's etcd member unable to reach the others, so it may never run the static pod and never rejoin; `playbooks/recover_in_cluster_mesh.yml` handles that by restarting the container, and if Headscale still does not answer, running a temporary Headscale container, from the image the role keeps in the host's own Docker for this, on the same configuration and state in the k3s container's network until the node is back on the mesh. The bootstrap server stays reachable on its direct address throughout (its k3s API port and Headscale's port are both published on the host). Prefer `headscale_hosted` on a separate machine when that matters.

Headscale's database lives on the bootstrap server's k3s data volume, and a static pod cannot use a replicated persistent volume instead, since kubelet runs it with no API server to bind a claim. So the provider requires Litestream: set `github_runner_cluster_headscale_litestream_replica` (see [Backups and a warm standby](#backups-and-a-warm-standby) for the settings), and the pod gets a `litestream-restore` init container and a `litestream` sidecar. A rebuilt bootstrap server then restores the database before Headscale starts, with the same data loss as `headscale_hosted`. The Noise key copy in `keys/` sits on the host, outside the k3s volume. It survives losing that volume but not the host, so supply `github_runner_cluster_headscale_noise_private_key` too if the host itself may be replaced. To run without Litestream, set `github_runner_cluster_headscale_accept_node_local_state: true`, and accept that losing that volume loses every registration: every node must then join again with a new key. There is no standby for this provider; recovery is rebuilding the bootstrap server.

## etcd timing

k3s's embedded etcd runs with a 100 ms heartbeat interval and a 1000 ms election timeout. Where the servers' peer traffic goes through a relay, as it does when each node's container sits behind NAT, round trips and jitter can exceed that: followers miss heartbeats, elections repeat, reads against etcd fail as Unavailable and k3s exits and restarts, which kills the pods on that node. `github_runner_cluster_etcd_heartbeat_interval` and `github_runner_cluster_etcd_election_timeout` (milliseconds, both empty by default so k3s's own timing applies and nothing changes for an existing fleet) raise them. When set, `env.j2` writes them into each server's `.env`, Compose passes them into the container, and `k3s/node-entrypoint.sh` adds `--etcd-arg=heartbeat-interval=<ms>` and `--etcd-arg=election-timeout=<ms>` to `k3s server`, on the mesh and when a self-hosted bootstrap server starts off it. Agents run no etcd and take neither.

```yaml
# group_vars/github_runner_cluster.yml
github_runner_cluster_etcd_heartbeat_interval: 500
github_runner_cluster_etcd_election_timeout: 5000
```

The role checks, before it changes anything on a host, that both are positive whole numbers, that they are set together or not at all, that the election timeout is at least five times the heartbeat interval (etcd refuses to start otherwise), and that every server of the group has the same two values, read from the inventory. etcd requires identical timing on every member, so set them once for the whole group.

A change reaches a server when the role recreates its container, which restarts k3s there. Edit the inventory once, then either run the role against every server together, which restarts all the control-plane nodes at about the same time and so takes the API down until a majority is back, or roll it out one server at a time with `--limit <server>`, waiting for that node to be Ready before the next (the identical-values check reads the whole group's inventory, so a limited run passes). Members briefly disagree either way. The role cannot see the timing the running servers use, so it does not warn when they differ: after a rollout that stopped partway, compare each server's `/var/lib/rancher/k3s/server/db/etcd/config`, which holds `heartbeat-interval` and `election-timeout` once they were passed.

An `--etcd-arg` is global: k3s also gives it to the temporary etcd it starts on every restart against an already-initialised datastore, never on a first boot. An earlier `listen-peer-urls` override broke exactly that restart, and only that one (see the first of the known issues in the [repository README](../../README.md) about `--etcd-arg`). These two arguments do not change what etcd binds to, but test a restart of an already-initialised datastore with them set before relying on them: `tests/mesh/run.sh` does that for the `hosted` scenario, restarting one server after the cluster is up. A timing that is too slow for the relay also lengthens how long a real leader failure takes to notice, so raise them only as far as the observed round trips need.

## Memory-pressure regrading

A server on a laptop or a small board can run short of memory while it still holds an etcd vote. Without this the choices are to leave it running whole and risk the node, or to stop it and lose the vote. `github_runner_cluster_regrade: true` lets a server step down while it keeps its etcd seat, and step back up. It is off by default and changes nothing on a running node until it is turned on.

There are three levels, from the most capable down:

- `full`: the server as it runs: control plane, etcd and workloads.
- `control-plane`: still a server and an etcd voter, tainted, cordoned and drained, so it runs no workloads.
- `etcd-only`: k3s runs with its API server, controller manager, scheduler and agent switched off (`--disable-apiserver`, `--disable-controller-manager`, `--disable-scheduler` and `--disable-agent`), so the server holds its etcd member and little else.

Giving up the vote is never part of it: a server that leaves etcd would have to be removed from the member list, which on a partition is unsafe, and k3s removes an etcd member when its Node object is deleted. The Node object of a stepped-down server stays, with its etcd role label.

A `regrade` service runs beside the server's k3s container (in its own Compose profile, which the role adds when the variable is true). It reads the memory pressure of the Docker host's kernel, the `some` line's `avg300` of `/proc/pressure/memory`, and `MemAvailable`; both are needed, because pressure alone also rises on reclaim while plenty is available, and a low `MemAvailable` alone is normal once the page cache has filled. A server counts as over the limit when the pressure is at least `github_runner_cluster_regrade_pressure_threshold` percent and `MemAvailable` is under `github_runner_cluster_regrade_available_floor_percent` of `MemTotal`. It steps down one level after being over for `github_runner_cluster_regrade_sustain_seconds` without a reading under the limit in between, and waits `github_runner_cluster_regrade_cooldown_seconds` after any step before the next. The cooldown has to exceed the pressure window, or the next reading still holds data from before the step; the role refuses a shorter one. The defaults are multiples of the window and the sample period, so they follow if either changes. The threshold and the floor are reasoned starting points, not measurements: read the service's log with `docker compose --profile regrade logs regrade` on a real host and tune them.

With `github_runner_cluster_regrade_step_up: automatic` (the default) the service also steps back up by itself, one level at a time. A server counts as calm when the pressure is under the threshold and `MemAvailable` is at or above the floor, both, which is stricter than not being over the limit: a reading between the two ends the streak towards stepping down and the streak towards stepping up alike, so the server does not step both ways on the same noise. It steps up after being calm for `github_runner_cluster_regrade_sustain_seconds`, once the cooldown since the last step, in either direction, has passed, through the same Lease and peer check as a step down; stepping up restarts the server's etcd at the first level that leaves etcd-only, so it never starts while a peer is down. A server that cannot hold the higher level cycles down and up no faster than once per cooldown and sustain period, which is the sign it is too small for the workloads it is given. `manual` leaves stepping up to `fleet-regrade up`.

Steps are serialised across the whole cluster. A server starts a step only while it holds a Lease named `fleet-regrade` in `kube-system` and every other etcd-voting Node is Ready, so two servers never step at once, and a step never starts while a peer is down. A server at etcd-only is not Ready (it has no kubelet), which also means no other server steps down while one is etcd-only. The Lease expires on its own after `github_runner_cluster_regrade_lease_duration_seconds` if its holder never gives it back. Every call the service makes to the cluster goes to another server's API and never to the stepping server's own: at etcd-only the server has no API, and its own kubeconfig answers `apiserver disabled` on some servers. The service is given every other server of the group and then every host marked `github_runner_cluster_voter_eligible`, by the addresses the servers' certificates carry, and uses the first whose `/readyz` answers, chosen again before each step, for the Lease's release and whenever a step waits for the API, since which hosts are servers can change at run time.

A level is applied by the Docker actuator, which records it in a file on the k3s data volume, which the container's entrypoint reads at every start, and restarts the container when the change is between etcd-only and another level. Between `full` and `control-plane` nothing restarts, because both run the same k3s; the difference is the taint and cordon the service puts on the Node. The container is restarted, never created again, so the node's password and mesh identity are the ones the cluster already holds, and an Ansible run, which changes nothing a container is created from, cannot undo a step. A level survives the container being recreated and the Docker host restarting: a server stepped down stays down, with its cordon, until it is stepped up, whether by hand or, in `automatic`, by the service once memory has been calm. That includes a `docker restart` by hand and an Ansible run that recreates the container (a changed image or Compose setting): the server comes back at the level it was left at, and `fleet-regrade up` is the way back to `full`. The entrypoint also records, on the container's tmpfs, the level k3s started at; that is what the service reads as the level the node is at, since k3s hides its arguments from `/proc`. A server whose entrypoint predates this feature is at `full` until it next restarts.

A step that restarts the container returns only when etcd serves again, read from the container's log since it started, and, for a level that runs the agent, when the node reports Ready on a heartbeat from the new container. The Lease is released as soon as a step returns, so a step that returned early would let another server step on top of an etcd that has not come back.

The Node carries the label `github-runner.exadev.com/regrade-level` (`github_runner_cluster_regrade_level_label`) with the level as its value, from the first step down until the server is back at `full`. The role's wait for every node to be Ready leaves such a node out, so running the role against a fleet with a stepped-down server neither fails nor clears its node-password Secret. The heartbeat publishes the level beside each not-Ready node in `fleet-health.json`, and `scripts/fleet-alert.sh` does not count a stepped-down server as an outage; a heartbeat image that predates the field alerts on it as it would on any server that is not Ready, so update that image before turning regrading on.

By hand, in the project directory (the `.env` the role writes names the Compose files and project, so these act on the right one):

```sh
docker compose --profile regrade exec regrade fleet-regrade status
docker compose --profile regrade exec regrade fleet-regrade down   # one step down
docker compose --profile regrade exec regrade fleet-regrade up     # one step up
```

Both go through the same Lease and peer check as the watcher.

A native server (`github_runner_cluster_node_mode: native`, see [Native servers](#native-servers)) regrades the same way, through the systemd actuator (`files/regrade/fleet-regrade-systemd.sh`) instead of the Docker one. The role runs it as the systemd unit `fleet-regrade` on the host, as root, with the host's own `/proc/pressure/memory` and `/proc/meminfo`, k3s's own `k3s kubectl` and the admin kubeconfig k3s wrote while it ran whole, from scripts and settings under `/usr/local/lib/github-runner-k3s/regrade`; it installs `jq` and `procps` from the distribution's packages when the host lacks them (Debian and Ubuntu; elsewhere it refuses until they are installed). A level is recorded in `/var/lib/rancher/k3s/regrade-level`, which the `k3s` unit's `ExecStartPre` (`files/native/write-regrade-level.sh`) reads at every start: it writes the drop-in `/etc/rancher/k3s/server.yaml.d/50-regrade.yaml`, which turns off the API server, controller manager, scheduler and agent at `etcd-only` and sets nothing at any other level, and records the level k3s starts at in `/run/github-runner-k3s-server/regrade-level`, the unit's runtime directory, which the actuator reads. The `ExecStartPre` runs whether or not regrading is on, so turning it on or off changes nothing in the server's unit and restarts nothing. A step into or out of `etcd-only` restarts the `k3s` unit and returns once etcd serves again (k3s's `ETCD server is now running`, read from the journal of the unit's new run by its invocation id) and, for a level that runs the agent, once the Node is Ready on a heartbeat later than the restart. The unit's `KillMode=process` leaves the pods' containerd shims running when k3s restarts without its agent, so entering `etcd-only` stops the shims that are left, with the containers they run, as k3s's `k3s-killall.sh` finds and stops them; leaving it starts the agent, whose kubelet starts the pods again. The level outlasts a restart of the unit and a reboot, as a Docker server's outlasts its container, and a demotion to an agent forgets it, so a later promotion starts the server whole. A server turn of the role that restarts a server at `etcd-only` waits for its etcd, not its Node, which has no kubelet. By hand, on the host:

```sh
sudo fleet-regrade status
sudo fleet-regrade down   # one step down
sudo fleet-regrade up     # one step up
```

The role refuses regrading where it could not work, before it changes anything: on an agent (for a native host, the role it is to run after this run, which for a host marked `github_runner_cluster_voter_eligible` is the one recorded on it); where the server is the only one in the group, since a server at etcd-only needs another server's API; on the bootstrap server of a `headscale_in_cluster` mesh, whose Headscale server is a static pod on the kubelet that etcd-only switches off; and on a native host whose kernel exposes no memory pressure (built without `CONFIG_PSI` or booted with `psi=0`), which the service could not decide on. It also refuses to turn regrading off, or to remove the service or the `fleet-regrade` unit, while the server is below `full`, because nothing else would step it up: step it up first, then run the role again.

The service mounts the Docker socket, which is a permission cost: whatever runs in that container can start containers on the host with any mount. `docker-prune` has the same mount for the same reason, and the regrade service's scripts are mounted read-only from the project directory, not fetched at run time. Its Compose profile is separate from `server` and `agent`, so a host that does not enable regrading never builds or starts it. The image is built locally by Compose from `regrade/Dockerfile` (Alpine with bash, jq and the Docker CLI), the first time the service starts.

The decision logic lives in `files/regrade/fleet-regrade-core.sh` and calls only three functions of an actuator: `levels`, `current_level` and `apply_level NAME`. The Docker actuator is `files/regrade/fleet-regrade-docker.sh`, over `files/regrade/fleet-regrade-k3s.sh`, which holds what any actuator of a k3s server needs (the levels, their records, the Node label and the restart into etcd-only and out of it) and leaves the platform only where k3s runs, how it restarts and how its log is read; `files/regrade/fleet-regrade.sh` runs the core with the actuator the settings name. Another platform supplies its own three functions and uses the core unchanged; a NixOS image can take the core from a pinned release of this collection.

## Role controller

`github_runner_cluster_role_controller: true` turns on the ARC role's role controller, which measures which hosts are fit to hold an etcd vote, reports the swap of an unfit voter for a fit standby that it would make and carries a swap out when asked (see the ARC role's README, Role controller, and the repository README's Voter swap). Its dry run is on unless the ARC role's `github_runner_arc_role_controller_dry_run` says otherwise. While it holds the `fleet-regrade` Lease for a swap, every run of this role refuses to change a node. On a native server or eligible native host the role also runs the role actuator that a swap switches the host through ([Role actuator](#role-actuator)). It is off by default. This role holds the controller's inventory:

- `github_runner_cluster_voter_eligible` (per host, default false) marks a host the controller may promote to a voter or demote from one. The role prepares no host for promotion by marking it, so mark only a host that is, or has been staged as, a server.
- `github_runner_cluster_voter_pinned` (per host, default false) marks a voter the controller must never demote. Set each pin in the inventory with a comment saying why.
- `github_runner_cluster_voters` (for the group, default 3) is the number of voters the cluster is held at.

While the controller is on, the role refuses a target that is even, under 3, or without a place of headroom below `github_runner_cluster_max_servers` (a swap adds the new voter before it removes the old one, so the target is at most the maximum minus one), a datastore that is not etcd, and fewer eligible hosts than the target once any host is marked. With no host marked the controller only reports the voters.

The role publishes the two host settings as Node labels, `github-runner.exadev.com/voter-eligible` and `github-runner.exadev.com/voter-pinned` (`github_runner_cluster_voter_eligible_label` and `github_runner_cluster_voter_pinned_label`), by passing them to k3s as `--node-label` on every runtime: a Docker server or agent, and a native one. The kubelet writes its labels to its Node each time it starts and never removes one, so while the controller is on, or a host is marked eligible or pinned, a host carries both labels with the value `true` or `false`, and turning a setting off writes `false` over the `true`. A host that uses none of this gets no label and no extra Compose file, so a fleet that does not use the controller keeps every node's configuration as it is and no container is recreated by an upgrade. A host's labels change with its next run of the role and the recreation or restart that follows it.

Beside them the role publishes the medium of the host's link, `wired`, `wifi` or `unknown`, as `github-runner.exadev.com/link` (`github_runner_cluster_link_label`), read on the host in each run that publishes the other two (`tasks/link.yml`, with `files/node-link.sh`). A node in a container or a VM cannot read it itself: it sees a veth, or a VM's virtio NIC, whatever the host beneath it uses. On a Mac whose node's Colima profile is bridged (`network.mode: bridged` with `network.address: true` in the profile's `colima.yaml`), the medium is that of the interface the VM is bridged to (`network.interface`), which is not the interface the Mac's own traffic takes when macOS prefers another, such as an Ethernet adapter over the Wi-Fi the VM is bridged to; for any other Mac runtime it is that of the interface the Mac's default route leaves by. The medium of a Mac interface is the name of the hardware port `networksetup -listallhardwareports` lists it under: Wi-Fi is `wifi`, a port whose name says Ethernet or LAN (built-in Ethernet, Thunderbolt Ethernet, a USB LAN adapter) is `wired`, and any other is `unknown`. On Linux it is that of the interface the default route leaves by, from its `/sys/class/net` entry: a wireless phy is `wifi`, a device is `wired`, and a virtual interface (a bridge, a bond, a tunnel) is `unknown`, since the link beneath it is not read. The label is the medium as the last run of the role found it, so a host whose link changes (a cable plugged in, a Wi-Fi fallback) carries the new medium after its next run of the role and the recreation or restart that follows it, as for the other labels; a host that publishes them already is recreated or restarted by the first run that adds this one.


### The role directory and a former member

The hosts that publish these labels (the controller is on, or the host is marked eligible or pinned) also get the role directory: `fleet-role.d` in the Compose project directory, which the role creates empty on every Docker host and `docker-compose.fleet-role.yml` mounts read-only into both node services at `/etc/github-runner`. It is a directory and not two files because whatever writes into it replaces each file in one rename, which gives the file a new inode, and a bind mount of a single file keeps showing the old one. A host that uses none of the controller's settings keeps its Compose configuration, so no container is recreated by an upgrade. The directory holds two files, each absent until something that changes the host's role writes it, and `files/k3s/node-entrypoint.sh` reads them before it starts Tailscale or k3s:

- `role`, `server` or `agent`: a node service whose role the file does not name logs why and idles until it is stopped, so the server and agent services never run k3s together and a host whose role changed does not start the old one again through `restart: unless-stopped`. With no file each service starts as it always has.
- `join-url`, a server's URL (`https://<host>:<port>`): when it is not empty, the server joins that server instead of `K3S_JOIN_SERVER_URL` from `.env`, so a promoted host joins a current voter rather than the inventory's bootstrap host.

Whatever the directory holds, a server also idles while its datastore holds a tombstone (`server/db/etcd/tombstone`). k3s writes it when etcd reports that this member was removed from the cluster (`pkg/daemons/executor/etcd.go` at v1.34.1+k3s1), and at its next start moves the datastore aside and joins again as a new learner (`Register` in `pkg/etcd/etcd.go`), so a removed server whose container restarted would become a member again behind the back of whatever removed it. The tombstone is the only record of the removal that a host down at the time has. A native server's unit refuses to start on the same tombstone (its `ExecCondition`, `files/native/fleet-role-is.sh`).

A server never bootstraps a second cluster from a former member's host: with no join URL from either source, it passes `--cluster-init` when it has a datastore (`server/db`, which k3s reuses, ignoring the flag) or none at all (a first bootstrap), and when its datastore was moved aside by a demotion (`server/db.demoted` and no `server/db`) it does not start k3s and exits with a message, and its restart policy repeats the refusal until `join-url` names a current server. An idle service ends on `docker stop`'s signal like any other; idling never exits by itself, since the restart policy would start it again.

### Role actuator

On a native host the controller may switch or take a snapshot on, a server or a host marked `github_runner_cluster_voter_eligible`, the role runs the role actuator's watcher (a Docker host's is below) while `github_runner_cluster_role_controller` is true: the `fleet-role-actuator` unit, which runs `files/role/fleet-role-actuator.sh watch` as root from `/usr/local/lib/github-runner-k3s/role` (`tasks/role_actuator.yml`). It switches the host between its server and agent units when the controller asks through the host's Node, and does nothing on the API but read: the controller cordons, waits for runner pods, drains, taints, labels the level, removes the etcd member, cleans the Node's labels and annotations and uncordons, because an agent host has no credential that can evict pods and its own k3s is down while it switches. Turning the controller off, or a host's eligibility, stops and removes the unit, its kubeconfig and its join URLs; the scripts stay on every native host, since the role's own promotion and demotion run them.

**What the controller writes on the Node**, all under `github-runner.exadev.com/`: the label `desired-role` (`server` or `agent`), and the annotations `role-swap` (the swap's id, `<UTC %Y%m%dT%H%M%SZ>-<outgoing node>-<incoming node>`), `role-step` (`promote`, `step-down` or `rollback`), `role-join-node` (the node of the voter a promotion joins) and `snapshot-request` (a swap whose snapshot a remaining voter is to take). The watcher reads its Node at the pace regrading waits for a restarted server at (`POLL_SECONDS` in `files/regrade/fleet-regrade-k3s.sh`) and takes each step once: a step reported `done`, `failed` or `refused` for the swap is not taken again (what follows a failure is the controller's to decide), and a step whose `desired-role` does not go with it is refused. Finishing a demotion is taken until it is done.

**What it reports**, in the ConfigMap `fleet-role-actuators` in the platform namespace (the ARC role's `github_runner_arc_platform_namespace`), under the node's name, as JSON: `{"swap", "step", "phase", "role", "started_at", "at", "message", "snapshot"}`, `phase` being `running`, `done`, `failed` or `refused`, `role` what the role file names afterwards and `started_at` the host's time just before a unit was started, which the controller waits for a later heartbeat than. A report the API does not take is made again on the next pass, since every step can be taken again: a step whose report is not done is run again, and a finish of a demotion not reported done is run again while the Node still carries the swap's `step-down`, even when nothing of the server is left, when it only reports (on a Docker host the node container that carries kubectl is the agent just started, which has no route to the API for a while, so that report is lost more often than a native host's). The finish's own report replaces the step-down's, and the watch counts a step-down followed by a finish for the same swap as taken.

**Authority.** `promote`, `step-down`, `rollback` and `snapshot` are taken only while the regrade Lease (`kube-system/fleet-regrade`) is held, unexpired, by `fleet-role` with the swap's id in its `github-runner.exadev.com/swap-id` annotation (see [Runs during a voter swap](#runs-during-a-voter-swap)). Finishing a demotion needs no Lease: it runs once the role file names the agent (or names the server while the datastore holds k3s's tombstone, or while the Node asks for a step-down, whose failure on a node that is not Ready the controller follows with the removal) and the member is gone (a tombstone in the datastore, `etcd.k3s.cattle.io/removed-node-name` naming the datastore's member, `github-runner.exadev.com/role-member-gone` naming the swap the Node is in, which the controller sets once every remaining voter reports that etcd lists only the voters, or no etcd label on the Node), which can never cost quorum, so a host that was down while its member was removed finishes when it returns.

**The steps.**

- `promote`: refused unless the host is provisioned to be a server (its `server.yaml` is there) and holds no datastore a demotion did not move aside. It writes `server` to the role file, writes `server.yaml.d/20-fleet-role-join.yaml` (`server:` the join node's URL, from the `join-urls` file the role writes for every other server and eligible host, and `cluster-init: false`) and a persistent drop-in for the server unit setting `GITHUB_RUNNER_JOIN_HOST` to that URL's host, since the Tailscale wrapper otherwise waits for the inventory's join host, which may by then be an agent, then stops and disables the agent unit and enables and starts the server unit.
- `step-down`: takes the running server to `etcd-only` through regrading's own level (`write_level` and `restart_into` from `files/regrade/fleet-regrade-k3s.sh`) and stops the pods left without a kubelet (`stop_pod_shims`), then writes `agent` to the role file, before the controller asks for the member's removal, so that a restart of the server unit afterwards (its `Restart=always`, a reboot) cannot rejoin the cluster as a new learner, and stops the `fleet-regrade` unit, whose own condition is now the server unit's (`fleet-role-is server`), so that its `Restart=always` cannot start a watcher that would step the server back up.
- `finish-demote` and `rollback`: write `agent` to the role file, stop and disable the server unit, forget its regrading level, move `server/db` aside to `server/db.demoted` (one copy), remove the join drop-ins and enable and start the agent unit. A rollback is the controller's for a candidate that did not become a voter.
- `snapshot`: `k3s etcd-snapshot save --name fleet-role-<swap id>` through the server's own supervisor, with the server's token from its data directory, reporting the names of the files k3s created.

A switch the role makes and one the actuator makes never run together: both hold the host's switch lock (`flock` on `/var/lib/rancher/k3s/fleet-role.lock`). `fleet-role-actuator` is on the PATH as root for a step by hand (`promote ID`, `step-down ID`, `rollback ID`, `snapshot ID`, `finish-demote`) and for `status`, which prints the role file, both units, the datastore, the joins and the last report. Its exit status is 0 when the step is done, 1 when it failed (the host is left with at most one role's unit running and a role file naming that role), 2 when it was refused with nothing changed (the Lease, a host that is not provisioned, a role file that names no role, a step it does not take, or the step's own precondition, each named), and 3 when a demotion cannot be finished yet.

**Its credential.** The role applies, through another server's API, the ServiceAccount `fleet-role-actuator` in the platform namespace with a ClusterRole that can `get`, `list` and `watch` Nodes, a Role that can `get` the regrade Lease by name, a Role that can `get` and `patch` the report ConfigMap by name, and a token Secret the token controller fills (`templates/role-actuator-rbac.yaml.j2`); it creates the ConfigMap when there is none, and writes a kubeconfig holding the token to `/etc/rancher/k3s/fleet-role-actuator.kubeconfig`, mode 0600, by a task that logs nothing. The watcher reaches the cluster through the first of the other servers and eligible hosts whose `/readyz` answers (`KUBE_SERVERS`, as regrading does), never through its own host's API. It needs `jq`, `ps` and `flock`, which the role installs on Debian and Ubuntu when the host lacks them and refuses the run for otherwise.

**On a Docker host** the watcher is the `role-actuator` service of the host's Compose project, on a server or a host marked eligible while the controller is on (`tasks/role_actuator_docker.yml`): an Alpine image with `bash`, `jq`, util-linux's `flock` (BusyBox's takes no timeout, which the switch lock waits with) and the Docker CLI with its Compose and Buildx plugins (`files/role/Dockerfile`), running the same `fleet-role-actuator.sh` with the Docker platform (`files/role/fleet-role-actuator-docker.sh`) from the project's `role` directory, where the role places the scripts, the settings, the kubeconfig and the join URLs. Its own Compose file, `docker-compose.role-actuator.yml`, which the role templates and names only in the Compose command for this service, mounts the Docker socket, the project directory at its own absolute path, so that the paths a Compose command in the container passes the daemon are the host's, and the server's `k3s-data` volume where the server's container mounts it. The steps are those above with containers for units:

- `promote` writes `server` and the join URL into the role directory (`fleet-role.d/role` and `join-url`, which the entrypoint reads), stops the `k3s-agent` service, copies the node's identity from the stopped agent's volumes into the server's (`<project>_k3s-agent-node` to `<project>_k3s-node` and `<project>_k3s-agent-tailscale-data` to `<project>_k3s-tailscale-data`) and starts the `k3s` service. When the server's container does not come up it starts the agent's again, with the role file naming it, and reports the failure: a Docker host with neither node container up cannot reach the API to be rolled back.
- `step-down` restarts the server's container at `etcd-only` through regrading's Docker actuator (`write_level` and `restart_into` from `files/regrade/fleet-regrade-docker.sh`), whose restart stops every pod process in it, then writes `agent` to the role file and stops the `regrade` service's container.
- `finish-demote` and `rollback` stop the server's container, move `server/db` aside and forget the level in its data volume, remove the join URL, copy the identity back into the agent's volumes and start the `k3s-agent` service.
- `snapshot` runs `k3s etcd-snapshot save` in the server's container.

The identity moves through `files/node-identity.sh`, the same pipe that seeds a node's password volume ([Node passwords](#node-passwords-and-recreating-servers)): one `docker cp` out of the stopped container straight into another, into a throwaway container created from the node's image and never started, so the node password and the Tailscale state are on no disk of the host, in no command line and in no output, and it refuses while either container runs. The node therefore keeps its name, its node password and its Tailscale device and address. The actuator's container is on no tailnet, so it runs kubectl in whichever node container is up with Tailscale running, with its kubeconfig on kubectl's standard input. The `regrade` service, which the role directory is mounted into too (`docker-compose.fleet-role.yml`), idles while the role file names another role than the server, as the k3s containers do, so a host stepped down or demoted for a swap is never stepped back up by it. Turning the controller off, or a host's eligibility, removes the service's container, its kubeconfig, join URLs and Compose file.

## Networking

Every node's k3s uses its mesh address for everything: its node IP, etcd's peer URLs, the API server and pod traffic. Which physical path the mesh takes between two nodes is Tailscale's choice, among the endpoints each node's Tailscale client can offer its peers. On Compose's default bridge network (`github_runner_cluster_network_mode: bridge`, the default) the client sits behind the Docker host's NAT and, inside a Docker VM, behind the VM's too, so it has no address its peers can reach and every pair of nodes is relayed, even on one LAN.

`github_runner_cluster_network_mode: host` runs the node's container on the Docker host's own network instead (`docker-compose.host-network.yml`, merged last). Its client then offers the host's own addresses, so nodes that share a network connect directly and fall back to a relay or a hole-punched path when they do not. The container publishes no port, since its ports are the host's; with `github_runner_cluster_wait_for_nodes` or `github_runner_cluster_record_deployed_version` on, the role checks that the API server answers on the host's loopback before it uses the kubeconfig there. k3s's ports, routes and firewall rules, Tailscale's, and the entrypoint's unreachable route for the mesh ranges then live in the host's namespace, shared with any other container on the host network there. Nothing k3s uses changes, so a node moves between the two modes with a container recreate.

On the host network the node's ports are the Docker host's. The API server (6443) and kubelet (10250) then answer on every address the host has, so on a bridged VM they are reachable from the LAN on the VM's address; etcd stays on loopback and the mesh address. In bridge mode only the API server's port is published, on the Mac's own addresses. Any other container on the same Docker engine would gain a route into the mesh through the node's Tailscale routing and its kube-proxy rules, so the host network needs a Docker engine dedicated to the node, and the role enforces it: before changing anything it refuses (under `--check` too) while the engine has a running container that is not part of the node's own Compose project (`github_runner_cluster_compose_project`: the k3s container, the pruner and the regrade service), naming each. A bridged Colima profile of its own per node meets it; a node that shares its engine with other containers, a second cluster or a Headscale server included, stays on the bridge network.

On a Linux machine running Docker without a VM, the host network is the machine's own. The node's Tailscale client would then create `tailscale0`, Tailscale's routing table and rules and its firewall chains beside the machine's own Tailscale client, and a second node on the same Docker host would share all of that and the kubelet's port. Neither works, so the role refuses host mode when the Docker host's network already has a Tailscale device that is not the node's own (as it is once the node runs on the host network), and a node that should go direct on such a machine needs a VM of its own.

Host mode needs the Docker host to have an address on the LAN the nodes share, given as `github_runner_cluster_lan_cidr`: before starting the node, the role reads the host's addresses from a throwaway container on the host network (`github_runner_cluster_network_probe_image`) and fails, changing nothing, when none lies in that network. Whenever the node's running container is on the other kind of network than the one asked for, Compose is about to recreate it, so the role first refuses unless the cluster stays safe without the node: the other servers whose node is Ready and whose own API server reports etcd healthy (`/readyz/etcd`, read through each server's container on its host) must still be a majority of all servers, and no ARC runner pod that has not finished may be on the node (cordon it and let its jobs finish). What cannot be told refuses the move: a cluster that cannot be read, servers the cluster does not label as servers, a server node that is missing, a server the inventory does not hold, or a server that cannot be reached. Only one node may move per run, since each host's checks see the others as healthy before any is recreated. All of this runs before the role changes anything, under `--check` too, and only reads (the address probe pulls its small image if the host lacks it). The check does not see which server leads etcd; the runbook below moves leadership off a node by hand.

On macOS the Docker host is a VM, which needs an address of its own on the LAN, and the role does not create VMs or change their network (it changes a Colima VM's memory and CPUs only; see [Container runtime after a reboot](#container-runtime-after-a-reboot-macos)). With Colima that means a profile created bridged: a profile's network mode is fixed when it is created and its LAN address cannot be turned off afterwards, so an existing user-mode VM cannot be converted, and a node moves to a new profile instead. Docker Desktop has no bridged VM network.

### Moving a node to a bridged Colima VM

One node at a time. The node keeps its identity because its three volumes move with it: the k3s data (etcd member, certificates, token), the Tailscale state and the node password (`k3s-node`, mounted at `/etc/rancher/node`), so its mesh address, node IP and etcd peer URL stay the same and nothing re-joins. Run every `docker` command below against the engine it names (`docker --context <context> ...`).

Before stopping anything:

1. **Check etcd on every server.** On each server, `docker exec <container> kubectl get --raw '/readyz?verbose'` lists `[+]etcd ok`. k3s ships no `etcdctl`, so read the members' health and the leader with one in a throwaway container that shares a healthy server's network namespace and reads its certificates from the k3s data volume, using an etcd image of the version the k3s release embeds (its release notes name it):

   ```
   etcdctl() {
     docker run --rm --network container:<container> -v <project>_k3s-data:/var/lib/rancher/k3s:ro \
       --entrypoint etcdctl gcr.io/etcd-development/etcd:<etcd version> \
       --cacert /var/lib/rancher/k3s/server/tls/etcd/server-ca.crt \
       --cert /var/lib/rancher/k3s/server/tls/etcd/client.crt \
       --key /var/lib/rancher/k3s/server/tls/etcd/client.key "$@"
   }
   etcdctl --endpoints https://127.0.0.1:2379 endpoint health --cluster
   etcdctl --endpoints https://127.0.0.1:2379 endpoint status --cluster -w table
   ```

   Every member must be healthy and started, and the other servers must stay a majority without this one. Record each member's ID and peer URL for the checks after the move.
2. **Move etcd leadership off the node** if `endpoint status` shows it as the leader. k3s has no command for it ([k3s docs, "Using etcdctl"](https://docs.k3s.io/advanced), [archived](http://web.archive.org/web/2026/https://docs.k3s.io/advanced)); with the function above, run `etcdctl --endpoints https://<this node's mesh address>:2379 move-leader <another member's ID in hex>` and read `endpoint status` again.
3. **Take an etcd snapshot as the last resort,** on another server: `docker exec <container> k3s etcd-snapshot save --name before-network-move`.
4. **Empty the node of jobs.** `kubectl cordon <node>`, then wait until `kubectl get pods --all-namespaces --field-selector spec.nodeName=<node>` lists no runner pod.

The new engine:

5. **Choose the bridged interface.** Pick a wired one where the host has one: the VM then reaches its peers without the host's Wi-Fi. A profile bridged to an adapter that is missing when the VM starts (an undocked laptop's dock adapter) does not start at all: `colima start` fails, and every container in that VM stays down until the adapter is back. Bridging over Wi-Fi works, through macOS's MAC NAT, so the router sees a second lease on the Mac's own Wi-Fi MAC. The interface is not fixed when the profile is created: a stopped profile started again with another `--network-interface` came back on that interface in testing, so a node bridged over Wi-Fi now should later move to a wired adapter with a stop and a start of its profile, not another profile and volume move. That has been seen with a test profile, not yet with a node on it.
6. **Give the new profile a home of its own whenever another profile already runs in the default home** (`~/.colima`): VMs in one home share its user-mode network daemon. Create the `COLIMA_HOME` directory before running any `colima` command with it, since Colima falls back silently to `~/.colima` when it does not exist.
7. **Approve Colima's network helper once.** The first start of a profile with an address installs `socket_vmnet` and a sudoers entry for it, which an administrator approves once per host.
8. **Stop the node and keep its image.** Run `docker update --restart=no` and `docker stop` on the node's container, so nothing starts the old copy again. Then `docker save` the node's image under the name its container uses, so the new engine runs the same build rather than building one.
9. **Export the three volumes with the container stopped,** so the etcd data is consistent. Use a throwaway container that tars each volume to a file, and never print the node password volume's file: carrying it avoids a `NodePasswordValidationFailed` event when the node registers again. The image's `agent/containerd` directory can be left out of the k3s data; kubelet pulls its images again.
10. **Create the bridged profile**, sized for what the node runs: Colima's default VM is far smaller than a server that also runs runner pods needs. For example `colima start --profile <name> --vm-type vz --cpus <n> --memory <GiB> --disk <GiB> --network-address --network-mode bridged --network-interface <interface> --activate=false`. `--activate=false` leaves the host's current Docker context alone; without it Colima switches every other Docker client on the host to the new VM. Check that `colima status --profile <name> --json` reports an `ip_address` on the LAN. On a memory-tight host, quit the old Docker engine first. Set `github_runner_cluster_colima_memory_gib` and `github_runner_cluster_colima_cpus` for the host to the same sizes, so a later change of size goes through the role and its quorum guard.
11. **Import onto the new engine.** `docker load` the image, create the three volumes as Compose would, with its labels (`docker volume create --label com.docker.compose.project=<project> --label com.docker.compose.volume=<volume> <project>_<volume>`, for `k3s-data`, `k3s-tailscale-data` and `k3s-node`), and untar each export into its volume.

Move the engine first and the network after, one change at a time, so that the second change goes through the role's guard:

12. **Create the node on the new engine, still on the bridge network:** in `github_runner_cluster_dir`, whose `.env` the last run of the role wrote for the bridge network, run `docker --context <new context> compose --profile server create --no-build k3s`.
13. **Start it through the role.** Point the host's `github_runner_cluster_docker_context` at the new profile's context, leave `github_runner_cluster_network_mode` as it is, and run the role for this host alone (`--limit <host>`, after a `--check --diff` run). It starts the node from the loaded image, building nothing. This is the first start on the new engine, after which the old copy must never run again (see the rollback limits).
14. **Check the node kept its identity.** It is Ready with the same InternalIP; `endpoint status` from step 1 lists the same member IDs and peer URLs, every member healthy; `tailscale status --self` in the node's container shows the same device and mesh address, and no new device has joined the tailnet; the node's log has no `membershipError`; no `NodePasswordValidationFailed` event names it (`kubectl get events --all-namespaces --field-selector involvedObject.name=<node>`); and `kubeconfig/kubeconfig.yaml` in `github_runner_cluster_dir` has been rewritten since the start, which shows the bind mounts reach the host through the new VM's mount of the host's directories.
15. **Move it to the host network through the role.** Check etcd again and move leadership off the node if it leads (steps 1 and 2), set `github_runner_cluster_network_mode: host` and `github_runner_cluster_lan_cidr`, and run the role for this host alone again. The node's container is now running on the bridge network, so the role's guard reads the cluster before Compose recreates it on the host network, and refuses while the cluster needs the node. Do not start or recreate it by hand: until the role has rewritten `.env`, `COMPOSE_FILE` names only the bridge network's files.
16. **Check it again,** as in step 14, and that `tailscale status` shows `direct` paths to every peer that is bridged too. A node on a user-mode VM never gets a direct path to a bridged one, because macOS Local Network privacy drops the user-mode VM's traffic to other Macs, so the benefit arrives once two nodes are bridged.
17. **Uncordon the node.**
18. **Make the new profile start with the host, and the old one not.** `brew services start colima` runs `colima start -f` for the default profile in the default home only ([Colima FAQ](https://github.com/abiosoft/colima/blob/v0.10.3/docs/FAQ.md), [archived](http://web.archive.org/web/2026/https://github.com/abiosoft/colima/blob/v0.10.3/docs/FAQ.md), and Homebrew's service definition for the formula). A profile with another name or home needs a launchd job of its own that runs `colima start --profile <name>` with its `COLIMA_HOME`, which the role installs on every run for the profile of the pinned Docker context (a daemon at boot for the profile named `node`, an agent at login for any other; see [Container runtime after a reboot](#container-runtime-after-a-reboot-macos)). Whatever started the old engine must no longer start the old copy of the node, which the collection does not manage.

**Rollback limits.** Starting the old container again on the old engine is safe only until the node's first start on the new one. After that the moved etcd member has appended to its log and voted, and the old copy would come back behind what the cluster believes it stored. Roll back by exporting the new volumes back the same way, or by removing the node (`kubectl delete node`, which removes its etcd member) and joining it fresh. Never run both copies at once: they are the same mesh node and the same etcd member.

Tailscale settings a node needs go on the `tailscaled` command line in `k3s/node-entrypoint.sh` or through `--vpn-auth`'s `extraArgs`: k3s runs `tailscale up --reset` on every start, which drops any other preference.

## Multiple sites

Each site is its own cluster: its own inventory group, bootstrap server and mesh provider, run by its own play with `github_runner_cluster_group` set to that group (see `examples/two-site/`). One cluster spanning two meshes is not supported: flannel's tailscale backend carries pod traffic over the single mesh every node belongs to, so every node of a cluster must be on the same tailnet or Headscale server. An inventory host belongs to at most one cluster group; to run a second cluster on the same machines, give each machine a second inventory host (see [Several clusters on one host](#several-clusters-on-one-host)).

## Several clusters on one host

A machine can run a node of a second, independent cluster beside a node of the first, for example to rebuild a cluster on another mesh (a different tailnet, a new k3s token, a fresh etcd) and move the runners to it before the first is removed. Each cluster is its own inventory group with its own play (`github_runner_cluster_group`), and the machine appears in each group as its own inventory host, both with the same `ansible_host`. The two nodes share the machine's Docker daemon, so the second cluster's hosts need their own values of everything that names something on it:

- `github_runner_cluster_container_name` and `github_runner_cluster_agent_container_name`: container names are unique on a daemon.
- `github_runner_cluster_api_port`: the port the server's API listens on inside its container, publishes on the Docker host and writes into its kubeconfig (`https://127.0.0.1:<port>`), and that joining nodes dial, so it is set once for the whole group. On a Mac every VM's published ports are forwarded to the Mac's own loopback, so it must differ from the first cluster's even when the second runs in a VM of its own. A port other than k3s's own 6443 adds `docker-compose.api-port.yml`, which starts k3s with `--https-listen-port`; the default adds nothing, so a cluster on the defaults keeps exactly the container configuration it had before the port was configurable and upgrading recreates none of its servers.
- `github_runner_cluster_compose_project`: Compose names the node's volumes (datastore, mesh identity, node password) and its image after the project.
- `github_runner_cluster_dir`: the directory holds the project's `.env` and the kubeconfig.

Before it writes anything to a host the role reads every container on its daemon and refuses to go on when a container of another Compose project, or of none, already has one of this cluster's container names, publishes this server's API port, or runs from this cluster's directory, naming each one. It also refuses an API port that is not a port number, hosts of one group that use different ports, and container names Docker would refuse or that are the same. Under `--check` the same read runs, so a dry run against hosts that run the first cluster shows whether the second fits.

The two nodes share the Docker host's memory, CPU and kernel limits. Each k3s server needs its own memory beside the pods scheduled on it, and both nodes' kubelets, containerd and pods draw on the same `fs.inotify.max_user_instances`, which a small VM may set low; measure both on the host before adding the second node. Each mesh device is the node's own container, so the two nodes are separate devices even when they are on the same tailnet and share a node name, and a name that is already a device there registers with a suffix (see `github_runner_cluster_node_name`). Each cluster's ARC role installs into the cluster its own kubeconfig reaches, so an org can have scale sets in both clusters at once; a runner scale set's name can belong to only one controller at a time, so a scale set is moved by uninstalling it from one cluster before installing it in the other, and the ARC role's validation refuses an inventory that registers one scale set from both.

Each Compose project runs its own `docker-prune` service against the same daemon. Two of them do the same work and are harmless.


### A Docker host's recorded role

A Docker host marked `github_runner_cluster_voter_eligible` keeps its role in its role directory, as a native host keeps its role in its role file: the first run records the inventory's role in `fleet-role.d/role` (`github_runner_cluster_docker_role_file`) when nothing is recorded there, and never writes over a recorded role, since the controller that moves votes changes it at run time and a run of the role must not undo that (`tasks/docker_role.yml` decides, with `cluster_host_role` in `plugins/filter/cluster_role.py`, which the native node shares; `tasks/docker_role_record.yml` records). The recorded role picks the Compose profile, the container the run starts and checks, whether the host takes a server's turn (`tasks/start_servers.yml` gives a turn to every host of the play whose role is `server`, not to the inventory's list of servers), and whether the regrade service runs: it runs beside a server only, so an eligible host may keep `github_runner_cluster_regrade: true` across a swap and has the service removed while it runs as an agent. The quorum guard a planned restart passes (`tasks/restart_guard.yml`, for a move between networks or a Colima VM resize) counts the host by its recorded role too: one recorded as an agent is read through the other servers and has no etcd vote of its own to keep. A host that is not marked eligible gets no record and runs the inventory's role.

Every Docker host gets one `.env` (`templates/env.j2`), holding both node services' variables whichever role it runs. Each service interpolates only the variables it names, so a service's configuration is the same as from the `.env` its role was given before there was one, and no running container is recreated by the change.

A run refuses, before it changes anything, a host whose node containers run in another role than the one it is to run (a host not marked eligible whose inventory role changed, an eligible host whose container no longer matches its record), a host running both containers, and a host not marked eligible that has a role recorded, which the entrypoint would obey once the directory is mounted: starting the other profile beside a running node would register the node twice under one name, and switching a running Docker node's role is not something a run of the role does. The message says what to stop or set.

### Runs during a voter swap

The role controller holds the regrade Lease (`kube-system/fleet-regrade`, the Lease regrading takes for a step, with the holder `fleet-role`) for the whole of a voter swap, its annotation `github-runner.exadev.com/swap-id` naming the swap. While it holds it unexpired, every run of the role, Docker or native, refuses before it changes anything (`tasks/role_lease_guard.yml`, with `cluster_role_lease_guard` in `plugins/filter/cluster_guard.py`), so a run never recreates a container, restarts a unit or rewrites a node's configuration in the middle of a swap. The Lease is read through each server of the inventory and each host marked eligible, a Docker server's through its container and a native server's through `k3s kubectl`, and its expiry (renew time plus duration, as regrading judges it) is compared with the clock of the host it was read on. A Lease regrading holds, or one that has run out, does not stop the run; no server answering when one could not be read does, since the run cannot tell. `--check` reports the same refusals. The names are the role's constants (the Lease's own, `github_runner_cluster_regrade_lease_namespace` and `github_runner_cluster_regrade_lease_name`, which a Colima VM resize takes too, and `github_runner_cluster_role_lease_holder` and `github_runner_cluster_role_lease_swap_id_annotation`, derived, not settings).

## Variables

- `github_runner_cluster_dir` (default `~/.github-runner` on the target host): the directory the role manages as the host's Compose project. It copies the collection's `docker-compose.yml` and `k3s/` build context there, templates `.env` there, and k3s writes the kubeconfig to its `kubeconfig/` subdirectory, so the host needs no checkout of this repository. The kubeconfig holds the cluster's admin credentials. k3s writes it with mode 644, since on a host whose Docker runs containers as root the file is root's and the connecting user reads it through the bits for others, and the role makes the `kubeconfig/` directory 0700 for the connecting user, which keeps every other local user out.
- `github_runner_cluster_compose_project` (default `github-runner`): the Compose project name. Compose prefixes the node's named volumes with it, and those volumes hold the k3s datastore and the node's mesh identity, so changing it on a running host brings up a new, empty node. Because it is pinned rather than taken from the directory's name, `github_runner_cluster_dir` can move without losing the cluster.
- `github_runner_cluster_k3s_token` (required), `github_runner_cluster_tailscale_join_key`, `github_runner_cluster_tailscale_api_token`, `github_runner_cluster_headscale_api_key`, `github_runner_cluster_headscale_join_key`: secrets, as plain variables from any source Ansible reads.
- `github_runner_cluster_join_key_path`, `github_runner_cluster_join_key_listener`: where a join key the role creates is kept (see [Join keys](#join-keys)).
- `github_runner_cluster_group` (default `github_runner_cluster`), `github_runner_cluster_max_servers` (default 5), `github_runner_cluster_api_port` (default 6443, k3s's own; the same on every host of the group, see [Several clusters on one host](#several-clusters-on-one-host)), `github_runner_cluster_datastore` (`etcd`, the default, or `sqlite`, which makes the cluster a single server with every other host an agent).
- `github_runner_cluster_mesh` (default `tailscale`), `github_runner_cluster_mesh_tag` (default `tag:github-runner-node`), `github_runner_cluster_pod_cidr` (default k3s's `10.42.0.0/16`).
- `github_runner_cluster_tailnet_domain`: the mesh's MagicDNS domain. Each node's address is `<node name>.<domain>`, and join URLs and TLS SANs use it.
- `github_runner_cluster_headscale_*`: the Headscale providers' settings, documented in `defaults/main.yml`.
- `github_runner_cluster_k3s_version`, `github_runner_cluster_tailscale_version`: the pinned image tags every node is built from, `github_runner_cluster_allow_k3s_version_jump` (default false) to skip the comparison with what runs, and `github_runner_cluster_cluster_read_timeout` (default 30, a positive whole number of seconds) for each server's read (see [Versions](#versions)). `github_runner_cluster_k3s_tested_version` is the k3s default, which the minor-version check compares hosts that set nothing against; set `github_runner_cluster_k3s_version` instead.
- `github_runner_cluster_node_name`: the k3s node name and mesh hostname, defaulting to the inventory name.
- `github_runner_cluster_node_taints`: Kubernetes taints (`key=value:Effect`, no spaces) the host's node registers with, empty by default. `NoSchedule` keeps pods without a matching toleration off it and `NoExecute` also evicts the ones already there. k3s applies them on every registration, so they come back if the node object is deleted, which a taint set with `kubectl` does not.
- `github_runner_cluster_etcd_heartbeat_interval`, `github_runner_cluster_etcd_election_timeout`: etcd's timing in milliseconds for every server, empty by default (k3s's own). Set together, the same on every server, the election timeout at least five times the heartbeat interval; see [etcd timing](#etcd-timing).
- `github_runner_cluster_role_controller` (default false), `github_runner_cluster_voters` (default 3), `github_runner_cluster_voter_eligible` and `github_runner_cluster_voter_pinned` (per host, default false): the role controller's inventory (see [Role controller](#role-controller)). `github_runner_cluster_voter_eligible_label` and `github_runner_cluster_voter_pinned_label` are the Node labels they are published under, derived, never set directly.
- `github_runner_cluster_regrade` (default false): run the `regrade` service, or on a native server the `fleet-regrade` unit, which steps this server down under memory pressure while it keeps its etcd vote (see [Memory-pressure regrading](#memory-pressure-regrading)). Servers only, and a Docker host marked eligible, whose service runs only while its recorded role is server (see [A Docker host's recorded role](#a-docker-hosts-recorded-role)). `github_runner_cluster_regrade_pressure_threshold` (percent, default 10) and `github_runner_cluster_regrade_available_floor_percent` (default 15) are the limit; `github_runner_cluster_regrade_step_up` (`automatic`, the default, or `manual`), `github_runner_cluster_regrade_sample_seconds`, `github_runner_cluster_regrade_sustain_seconds`, `github_runner_cluster_regrade_cooldown_seconds`, `github_runner_cluster_regrade_operation_timeout_seconds` and `github_runner_cluster_regrade_lease_duration_seconds` are the timing, all derived from `github_runner_cluster_regrade_pressure_window_seconds` (the kernel's `avg300`, 300 seconds, not a setting) unless set. `github_runner_cluster_regrade_level_label` and `github_runner_cluster_regrade_taint` are derived, never set directly.
- Per-host overrides: `github_runner_cluster_node_role` (`server` or `agent`), `github_runner_cluster_bootstrap` (true picks the bootstrap host, false excludes a host), `github_runner_cluster_server_url` (join this server instead, for a cluster whose servers are outside the inventory), `github_runner_cluster_tls_sans`, `github_runner_cluster_node_address`, and `github_runner_cluster_voter_eligible` (true stages a native host as a standby server, its server configuration written and its name on every server's certificate, without making it a server; see [Native servers](#native-servers)). The run fails if the result has an even number of servers, no servers, or more than one bootstrap host.
- `github_runner_cluster_docker_context` (default empty): pins the Docker context this host's node runs in (see [Docker contexts](#docker-contexts)).
- `github_runner_cluster_network_mode` (default `bridge`, or `host`): the network the node's container runs on, and with `host`, `github_runner_cluster_lan_cidr` (required: the LAN the nodes share) and `github_runner_cluster_network_probe_image` (default `busybox:1.37`, for reading the host's addresses) (see [Networking](#networking)).
- `github_runner_cluster_runtime_autostart_at` (default `auto`; `login` or `boot`) and `github_runner_cluster_runtime_boot_profile` (default `node`): whether the Colima profile is started by a launchd agent at login or by a launchd daemon at boot, and which profile `auto` starts at boot (see [Container runtime after a reboot](#container-runtime-after-a-reboot-macos)).
- `github_runner_cluster_runtime_autostart` (default true), `github_runner_cluster_runtime` (default `auto`; `colima`, `docker_desktop` or `other`), `github_runner_cluster_colima_profile` (default empty, taken from the Docker context), `github_runner_cluster_colima_home` (default empty: the `COLIMA_HOME` is read from the endpoint of the profile's Docker context, and is unset for Colima's own `~/.colima`; set it only for a context that does not say, and the role passes it to colima and to the launchd agent), `github_runner_cluster_runtime_path` (default both Homebrew prefixes and the system directories): on a macOS host, start Colima at login through a launchd agent and check the runtime (see [Container runtime at login](#container-runtime-after-a-reboot-macos)).
- `github_runner_cluster_colima_memory_gib` and `github_runner_cluster_colima_cpus` (default empty, keeping the profile's own): a Colima host's VM memory in GiB and its CPUs, each a positive whole number, applied one node at a time through the quorum guard when the VM differs (see Colima VM size under [Container runtime after a reboot](#container-runtime-after-a-reboot-macos)). `github_runner_cluster_colima_memory_reserved_gib` (default empty) derives the memory instead, or bounds one set explicitly, from the host's memory less it and `github_runner_cluster_colima_memory_host_reserve_gib` (default 10, macOS's own), never below `github_runner_cluster_colima_guest_baseline_gib` (default 3.4) plus `github_runner_cluster_colima_runner_memory_limit_gib` (default empty, required by a derivation) rounded up. `github_runner_cluster_colima_resize_lease_seconds`, `github_runner_cluster_colima_resize_lease_holder`, `github_runner_cluster_regrade_lease_name` and `github_runner_cluster_regrade_lease_namespace` are derived, never set directly. `github_runner_cluster_native_runner_wait_timeout` and `github_runner_cluster_native_ready_timeout` bound the wait for the node's runner pods and for the node to come back, as they do for a native node.
- `github_runner_cluster_container_name` (default `github-runner-k3s`) and `github_runner_cluster_agent_container_name` (default `github-runner-k3s-agent`): the names of the node's server and agent containers, which a second cluster on the same Docker hosts sets to names of its own (see [Several clusters on one host](#several-clusters-on-one-host)).
- `github_runner_cluster_compose_files`: extra Compose files for the host's k3s project, merged after `docker-compose.yml`, as paths relative to `github_runner_cluster_dir` or absolute. Several nodes on one Docker host each need their own `github_runner_cluster_dir`, `github_runner_cluster_compose_project` and container names; nodes of one cluster share its API port, so all but one of them on a host also need an extra file that publishes none (`ports: !reset []`, as `tests/mesh` does).
- `github_runner_cluster_wait_for_nodes`: wait for every node of the inventory to be Ready afterwards, clearing the node-password registration of a replaced node that fails to rejoin (installs the kubernetes Python client through `github_runner_k8s_client`). The wait covers the nodes the inventory's hosts own, by their effective node names, and leaves out a server that memory-pressure regrading has stepped down and an inventory node that has not registered. A node the cluster holds that no inventory host owns (one flashed from an image and joined by hand, say) is never waited for: when it is not Ready the run prints one line with its name and status, and carries on. When no node of the inventory has registered, the run fails.
- `github_runner_cluster_server_ready_timeout` (default 600): the most seconds, about, the role waits for a recreated server's node to report Ready before the next server's turn (see [Node passwords and recreating servers](#node-passwords-and-recreating-servers)).
- `github_runner_cluster_k3s_prerequisites` and `github_runner_cluster_containerd_apparmor_stacking_fix` (both default `false`): the two host preparation steps (see [Host preparation](#host-preparation)). Per host, in its `host_vars`.
- `github_runner_cluster_node_mode` (default `compose`): how this host runs its k3s node, `compose` or `native` (see [Native nodes](#native-nodes)). Per host, in its `host_vars`.
- `github_runner_cluster_native_start` (default `true`): whether a native node's service is enabled, started and restarted when something it reads changed, and the node then waited for. `false` only installs and configures.
- `github_runner_cluster_native_ready_timeout` (default `github_runner_cluster_server_ready_timeout`): the most seconds, about, the role waits for a started native node to be Ready on a new heartbeat and on the cluster's tailnet, and a server also an etcd voter.
- `github_runner_cluster_native_demotion_min_voters` (3, not a setting): the fewest voters, every one Ready, a demotion leaves; three is the smallest etcd membership that keeps quorum through a failure.
- `github_runner_cluster_native_runner_wait_timeout` (default `github_runner_cluster_native_ready_timeout`): the most seconds, about, a switch between the server and agent units waits for the runner pods on the cordoned node to finish before it uncordons the node and fails, changing nothing else.
- `github_runner_cluster_native_k3s_download_url` (default k3s's GitHub releases): where the k3s binary and its sum file are downloaded from, as `<this>/<release tag>/<asset>`.
- `github_runner_cluster_native_k3s_sha256` (default empty): the SHA-256 of the k3s binary for this host's architecture, instead of the sum the release itself lists. Set it from a source other than the download to catch a release that was replaced.
- `github_runner_cluster_native_tailscale_install` (default `true`): whether the role installs the pinned Tailscale package from Tailscale's apt repository (Debian and Ubuntu). `false` leaves the host's client as it is and only checks its login.
- `github_runner_cluster_native_tailscale_repository_url` (default `https://pkgs.tailscale.com/stable`): where that repository's signing key and list file are fetched from, when the host has none.
- `github_runner_cluster_native_tailscale_leave_other_tailnet` (default `false`): whether the role logs a client out of another tailnet so that k3s can join the cluster's; `false` stops the run instead.
- `github_runner_cluster_role_actuator_dir`, `github_runner_cluster_role_actuator_service`, `github_runner_cluster_role_actuator_name`, `github_runner_cluster_role_actuator_configmap`, `github_runner_cluster_role_actuator_kubeconfig`, `github_runner_cluster_role_actuator_namespace` and `github_runner_cluster_role_actuator_commands` are derived: where the role actuator's scripts and settings go (on a native host `/usr/local/lib/github-runner-k3s/role`, on a Docker host the Compose project's `role` directory), its unit, its ServiceAccount, its report ConfigMap, its kubeconfig, the platform namespace it reports in and the commands its watcher needs with the package of each (see [Role actuator](#role-actuator)); `github_runner_cluster_api_candidates` is derived too, the other servers and eligible hosts whose API the regrade service and the role actuator reach the cluster through.
- `github_runner_cluster_docker_role_file`, `github_runner_cluster_role_lease_holder` and `github_runner_cluster_role_lease_swap_id_annotation` are derived: the file that records an eligible Docker host's role, and the role controller's holder name on the regrade Lease and the annotation naming its swap (see [A Docker host's recorded role](#a-docker-hosts-recorded-role) and [Runs during a voter swap](#runs-during-a-voter-swap)).
- `github_runner_cluster_native_agent_service`, `github_runner_cluster_native_server_service`, `github_runner_cluster_native_service`, `github_runner_cluster_native_join_url`, `github_runner_cluster_agent_server_url`, `github_runner_cluster_native_join_host`, `github_runner_cluster_native_role_file` and `github_runner_cluster_native_restart_marker` are derived: the units' names (`k3s-agent` and `k3s`), the unit of the host's role, the URL the node joins and the host in it, which the Tailscale wrapper waits for, the role file both units' conditions read, and the prefix of the per-unit file that says a restart is waiting; `github_runner_cluster_native_regrade_level_file`, `github_runner_cluster_native_regrade_started_file`, `github_runner_cluster_native_regrade_dir`, `github_runner_cluster_native_regrade_service`, `github_runner_cluster_native_regrade_commands`, `github_runner_cluster_native_agent_runtime_dir` and `github_runner_cluster_native_server_runtime_dir` are derived too: a native server's requested and started regrading levels, where its regrade scripts and settings go, the unit that runs them, the commands regrading needs with the package of each, and each unit's own runtime directory under `/run` (one per unit, since systemd removes a unit's runtime directory when its condition skips a start, which on a shared one would take the running unit's resolver file). `github_runner_cluster_native_drain_for` is derived as well: what `tasks/native/drain.yml` says was not done when it cannot empty the node, a role switch's by default, which a Colima VM resize passes as its own. `github_runner_cluster_native_bin_dir`, `github_runner_cluster_native_lib_dir`, `github_runner_cluster_native_config_dir`, `github_runner_cluster_native_unit_dir`, `github_runner_cluster_native_data_dir`, `github_runner_cluster_native_tailscale_cli`, `github_runner_cluster_native_apt_keyring`, `github_runner_cluster_native_apt_source`, `github_runner_cluster_native_run_dir` and `github_runner_cluster_native_psi_file` are where the native node's files live, which are not settings, and are variables only so the tests can point them at a stand-in.

## Examples

`examples/` in this repository has inventories for a single host on SQLite, three servers on Tailscale, each Headscale provider, and two sites, and for secrets from ansible-vault (`examples/ansible-vault/`), environment and file lookups (`examples/env/`) or 1Password (`examples/onepassword/`). The smallest:

```yaml
# inventory.yml
all:
  children:
    github_runner_cluster:
      vars:
        github_runner_cluster_tailnet_domain: example.ts.net
      hosts:
        node1:   # bootstraps the cluster
        node2:   # server
        node3:   # server
        node4:   # agent
```

```yaml
- hosts: github_runner_cluster
  roles:
    - exadev.github_runner.github_runner_cluster
```

with the secrets set from any source, for example:

```yaml
# group_vars/github_runner_cluster.yml
github_runner_cluster_k3s_token: "{{ vault_k3s_token }}"
github_runner_cluster_tailscale_join_key: "{{ lookup('ansible.builtin.env', 'TAILSCALE_JOIN_KEY') }}"
```

or read from 1Password by adding `exadev.github_runner.github_runner_secrets_onepassword` (with `github_runner_secrets_onepassword_consumers: [cluster]`) before it.

## Testing

`tests/litestream/run.sh` runs the `headscale_hosted` provider with Litestream and a warm standby against an S3-compatible store on this machine's Docker, registers a real Tailscale client, promotes the standby and checks that users, nodes and pre-auth keys survive, that the client reconnects and that the promoted server keeps replicating. It also checks that `headscale_in_cluster` refuses to run without Litestream. `.github/workflows/litestream.yml` runs it on pull requests that touch the Headscale providers.

`tests/mesh/run.sh` brings up three k3s nodes in Docker on one machine and joins them through Headscale with this role, for the `headscale_hosted` and `headscale_in_cluster` providers, and checks the `headscale_existing` policy check against a real server. Each cluster scenario runs the role a second time and fails if any node container restarted. Both set the etcd timing and check each server's etcd config file carries it, and the `hosted` scenario then restarts a joined server against its initialised datastore and checks the cluster recovers with the timing still in place. The `compose_faulty` scenario checks the role refuses a Compose release that has that fault. With `GRTEST_PIN_CONTEXT=1` the cluster scenarios pin `github_runner_cluster_docker_context` while the current Docker context the playbooks see points at a socket that does not exist, so any docker call that ignored the pin fails, and they check the current context is unchanged afterwards; `tests/litestream/run.sh` takes the same setting for the Headscale hosts it delegates to and the promotion playbook. The `context_checks` scenario checks the role refuses a pinned context that does not exist, and one set alongside `DOCKER_HOST`, before writing anything. The `host_network` scenario (Linux only) gives each node a Docker daemon of its own at a fixed address on the test network, standing in for a VM with an address on the LAN, runs the role with `github_runner_cluster_network_mode: host`, and checks that every node's Tailscale client reaches every other directly at that address and that no port is published. `tests/unit/test_cluster_network.py` checks the rendered Compose project in both modes and the role's list of Compose files; `tests/unit/test_cluster_guard.py` checks the address and quorum filters, and `tests/unit/test_host_network_role.py` runs the role's `tasks/host_network.yml` against stand-in `docker` and `kubectl` commands. `.github/workflows/mesh-integration.yml` runs them on pull requests that touch the role, the hosted scenario on 2.39.0, the first fixed release, as well as on a current one.

`tests/regrade` tests the regrading: the core's decision, stepping up by itself, and the Lease and peer coordination (`regrade-core.sh`, `regrade-recover.sh`, `regrade-lease.sh`) the Docker actuator (`regrade-docker.sh`), against stand-ins for `docker` and `kubectl`, and the systemd actuator with the server unit's `ExecStartPre` (`regrade-systemd.sh`), against stand-ins for `systemctl`, `journalctl`, `date`, `k3s` and `kubectl` and with real processes standing in for the pods' shims, all run by `tests/unit/test_regrade_shell.py`; `tests/unit/test_native_regrade.py` covers the role's regrading of a native server (its refusals, the unit and its settings, a server turn at etcd-only and turning it off); `tests/unit/test_cluster_regrade.py` covers the role's checks, the settings file, the Compose service, the levels the entrypoint starts k3s at and the tasks that remove the service.

`tests/unit/test_cluster_host_prerequisites.py` covers the [host preparation](#host-preparation) without a real host: the defaults, that both node modes include the steps at the right point, and the steps themselves (`tests/cluster_host_prerequisites/run.yml`) against stand-ins for `modprobe`, `sysctl`, `apparmor_parser` and `sudo` on `PATH`, with a k3s data directory laid out as k3s leaves it.

`tests/unit/test_runtime_autostart.py` covers the [container runtime tasks](#container-runtime-after-a-reboot-macos) without a Mac: it renders the launchd agent and daemon through `tests/runtime_autostart/render_plist.yml`, and runs `tasks/runtime.yml` and `tasks/end_checks.yml` through the role against stand-ins for `docker`, `colima`, `launchctl`, `plutil` and `sudo` on `PATH`, the stand-in `launchctl` refusing to change the system domain unless it was run through the stand-in `sudo`. It checks the variable defaults, that Linux hosts are left alone, that a second run changes nothing, that `--check` writes and starts nothing, and that each way the runtime or the node's container can be down fails with its message. `tests/unit/test_container_runtime.py` covers the filter that works out the runtime from the Docker context. Nothing there touches a real Colima, launchd or Docker Desktop, so loading the agent into a real login session, and the daemon starting a Colima VM at a real boot with no one logged in, are the parts only a run on a Mac can show.

`tests/unit/test_cluster_colima_size.py` covers the Colima VM size: the filters that read the profile's size (`plugins/filter/cluster_colima.py`) and take and give back the `fleet-regrade` Lease (`plugins/filter/cluster_guard.py`), and `tasks/colima_size.yml` run through the role (`tests/colima_size/run.yml`) against stand-ins for `docker` and `colima` that keep each profile's VM, the node containers, the cluster's nodes and the Lease as files. `tests/unit/test_cluster_wait_nodes.py` runs the wait for nodes to be Ready and its rescue against a stand-in for `kubectl`: a node outside the inventory that is not Ready is reported and never waited for, and an inventory node that stays not Ready still fails the run. `tests/unit/test_node_entrypoint.py` runs the entrypoint's guards in a shell with a stand-in for `sleep` ([The role directory and a former member](#the-role-directory-and-a-former-member)): the join URL's precedence, `--cluster-init` with a datastore, with one moved aside and with none, the idling of a service its role file does not name and of a server on a tombstone, a host with no role file starting as before, and the override that mounts the directory. `tests/unit/test_native_server.py` runs the native server unit's condition on a tombstone. `tests/unit/test_role_actuator.py` runs the [role actuator](#role-actuator) against stand-ins for `systemctl`, `kubectl` and `k3s` (`tests/role_actuator/`, over regrading's own in `tests/regrade/`) and the real `files/native/fleet-role-is.sh` as both units' condition: each step's success, failure, refusal (no Lease, a Lease for another swap, a host that is not provisioned, a role file that names no role, a desired role that does not go with the step) and report, a demotion finished without the Lease once a tombstone, k3s's removal annotation or a missing etcd label says the member is gone and not before, one moved-aside datastore kept, the join drop-ins written and removed, the switch lock, `status`, the watcher taking a swap through each step once, and, through the role, the watcher's unit, settings and kubeconfig on an eligible host, its credential scoped to reading Nodes and the Lease and patching its report, its token kept out of everything the role prints, nothing set up on a host the controller may not switch or under `--check`, and the regrade unit's condition. `tests/unit/test_node_password.py` covers [the node password volume and the servers' turns](#node-passwords-and-recreating-servers) without Docker: the filters in `plugins/filter/cluster_recreate.py`, the Compose file's volumes, and `tasks/node_password.yml`, `tasks/server_recreate_check.yml`, `tasks/server_ready.yml` and `tasks/start_servers.yml` run through the role (`tests/node_password/run.yml`) against a stand-in for `docker` that moves a real tar stream between its `docker cp` processes and keeps containers, volumes and node readiness as files, and a stand-in for the Compose module that recreates a container whose rendered hash differs and takes its node out of Ready until the role has waited for it.
