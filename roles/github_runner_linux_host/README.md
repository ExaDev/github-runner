# github_runner_linux_host

The host-level baseline of a Linux host that carries a k3s node, for a machine that is dedicated to the cluster. It does nothing on any other operating system, so it can be applied to a mixed inventory, and every step but the Tailscale update is off by default and behind a variable of its own, because each changes how the host behaves for whoever else uses it. `playbooks/site.yml` runs it before the fleet play, on every host of the cluster group; a fleet turns the steps on per host in `host_vars`. It touches neither the node nor the host's Tailscale client, which `github_runner_cluster` owns (see its [Native nodes](../github_runner_cluster/README.md#native-nodes)).

Its tasks that change the host use `become` on their own, so the connecting user needs passwordless sudo, or the play needs `--ask-become-pass`. Everything the role only reads runs as the connecting user, and under `--check` nothing is changed and each change a real run would make is reported. Every variable is checked against `meta/argument_specs.yml` when the role runs.

## Keeping the host awake

`github_runner_linux_host_keep_awake: true` masks `sleep.target`, `suspend.target`, `hibernate.target` and `hybrid-sleep.target`, and writes a systemd-logind drop-in (`/etc/systemd/logind.conf.d/90-github-runner-keep-awake.conf`) that sets `HandleLidSwitch`, `HandleLidSwitchExternalPower` and `HandleLidSwitchDocked` to `ignore`, then has logind read it with `SIGHUP`, which reloads its configuration without ending the login sessions it tracks. A host that suspends drops off the network, so its node leaves the cluster and its runner pods stop; a laptop suspends whenever its lid closes (logind's default for `HandleLidSwitch` is `suspend`), and its desktop or power button can ask logind to suspend it as well. Masking is what stops a request that does not come from the lid: the target cannot be started, so `systemctl suspend` fails. Both parts are idempotent, and the role checks what is masked before it masks anything.

## NetworkManager connectivity checks

The NetworkManager connectivity setting is not ready for use. Setting `github_runner_linux_host_networkmanager_connectivity_check_off` to either `true` or `false` fails without changing the host; leaving it unset leaves the configuration unmanaged. The watchdog is not installed by the role. Safe integration requires verified service readiness, exclusive control of drop-in writers, and preventing an in-flight NetworkManager reload from overlapping recovery. Scheduled deadlines use a suspend-aware boot clock and expire on a different boot.

## Wi-Fi power save

`github_runner_linux_host_wifi_powersave_off: true` keeps the host's Wi-Fi from power saving. A radio in power-save mode sleeps between beacons and delays or drops packets, which on a node of the cluster shows as the node flapping `NotReady`. It matters only for a host on Wi-Fi, and does nothing to a host without a Wi-Fi device. The mechanism depends on what manages the Wi-Fi, which the role reads from the host: NetworkManager when `nmcli` lists a Wi-Fi device that is not `unmanaged`, else systemd-networkd when it is running and the kernel has a Wi-Fi network device (one with a `phy80211` link under `/sys/class/net`). A host where neither manages a Wi-Fi device fails, since the setting is explicitly asked for; a host with no Wi-Fi device at all is left alone as long as one of the two answers.

### NetworkManager

The role writes `/etc/NetworkManager/conf.d/zz-github-runner-wifi-powersave.conf` with `wifi.powersave = 2` (disable), which sets the default for every connection that does not set its own, and has NetworkManager read it (`nmcli general reload conf`). NetworkManager applies a connection's power save setting each time it activates the connection, so that is what keeps it off across reconnects and reboots. The drop-in's name sorts after Ubuntu's `default-wifi-powersave-on.conf` (`wifi.powersave = 3`), because NetworkManager reads its configuration files in alphabetical order and the last one to set a value wins. To switch it off on a radio that is running now, the role runs `iw dev <device> set power_save off` for each Wi-Fi device that reports it on, which changes the radio without taking the link down; `nmcli device reapply` does not change a running radio. A host without `iw` is told so in the run, and gets the setting at the next activation of its connection.

### systemd-networkd

Nothing configures Wi-Fi power save here: neither `systemd.network` nor `systemd.link` (checked in the v259 manual pages, where the only wireless settings are matching ones such as `WLANInterfaceType=` and `Type=wlan`) nor netplan has such a setting, and the kernel's per-interface preference is set with `iw`. So the role installs `iw` with apt (a host that is not Debian or Ubuntu fails) and writes two files:

- `/etc/udev/rules.d/90-github-runner-wifi-powersave.rules`, which gives each Wi-Fi network device (`DEVTYPE=wlan`, set by cfg80211) a `SYSTEMD_WANTS` for the unit below when it is added, named by its final name (`$name`, after a `.link` file's rename), which is what systemd names the interface's device unit by. The role runs `udevadm control --reload` when the rule changes.
- `/etc/systemd/system/github-runner-wifi-powersave@.service`, a oneshot unit with `RemainAfterExit` that runs `iw dev <interface> set power_save off`. It is bound to and ordered after `sys-subsystem-net-devices-<interface>.device` (the same pattern as `wpa_supplicant@.service`), so it runs once udev has finished with the interface, has a status and a journal, and runs again if the interface goes away and comes back. The role runs `systemctl daemon-reload` when the unit changes.

The rule matches every Wi-Fi interface, so one that appears later (a USB adapter) is covered without running the role again. The setting survives a reconnect, because the kernel keeps it per interface; brcmfmac, for one, stores the preference and applies it each time it brings the firmware up. The unit has not run for an interface that is already up, so the role also runs `iw dev <interface> set power_save off` on each one that reports it on. Unlike the NetworkManager path, an `iw` that cannot read an interface fails the run, since there is no later activation to rely on. Not every driver supports the setting; one that does not makes the unit fail, and shows in `systemctl status github-runner-wifi-powersave@<interface>`.

Under `--check` both paths report each change and make none. A second run changes nothing.

A Wi-Fi-only node still drops when the radio does. These settings only stop the radio adding drops of its own; see [A Wi-Fi-only host](../github_runner_cluster/README.md#a-wi-fi-only-host).

## Making the host ready for k3s

`github_runner_linux_host_k3s_prerequisites: true` loads the kernel modules `overlay` and `br_netfilter` and sets the sysctls `net.ipv4.ip_forward`, `net.bridge.bridge-nf-call-iptables` and `net.bridge.bridge-nf-call-ip6tables` to 1, both now and at boot: a `modules-load.d` file (`/etc/modules-load.d/github-runner-k3s.conf`) and a `sysctl.d` file (`/etc/sysctl.d/90-github-runner-k3s.conf`) for boot, and `modprobe` and `sysctl -w` for now. Forwarding is what pod traffic between interfaces needs, and the bridge settings make bridged pod traffic pass through iptables, which services' NAT needs ([k3s requirements](https://docs.k3s.io/installation/requirements) ([archived](http://web.archive.org/web/2026/https://docs.k3s.io/installation/requirements))). k3s loads the modules and sets some of the sysctls itself as it starts, but the bridge sysctls only exist once `br_netfilter` is loaded, so the role loads the modules first. A module is loaded only when `/sys/module` does not list it, and a sysctl is set only when its value differs.

## Letting a container's processes signal each other under a stacked AppArmor label

`github_runner_linux_host_containerd_apparmor_stacking_fix: true` installs an AppArmor profile that replaces the one k3s's containerd generates for its containers. It is for a native k3s node on Ubuntu 26.04 LTS, and for no other host.

**Why a host needs it.** Ubuntu 26.04 (kernel 7.0, AppArmor 5) sets `kernel.apparmor_restrict_unprivileged_unconfined=1`. runc runs unconfined and without `CAP_MAC_OVERRIDE`, so when it changes a container's profile the kernel stacks `//&unconfined` onto the label: every container runs as `cri-containerd.apparmor.d//&unconfined`. The profile containerd generates (`contrib/apparmor/template.go` of [k3s-io/containerd](https://github.com/k3s-io/containerd)) allows `signal (send,receive)` and `ptrace` only with `peer=cri-containerd.apparmor.d`, the plain label, so the stacked label's signals to its own processes are denied. A .NET runtime whose garbage collector aborts is denied its `SIGABRT` as well, and glibc ends in `hlt`, which the CPU reports as a general protection fault. This is [containerd/containerd issue 14485](https://github.com/containerd/containerd/issues/14485) ([archived](http://web.archive.org/web/2026/https://github.com/containerd/containerd/issues/14485)), and [pull request 14487](https://github.com/containerd/containerd/pull/14487) ([archived](http://web.archive.org/web/2026/https://github.com/containerd/containerd/pull/14487)) adds the two rules that fix it, `signal (send,receive) peer=cri-containerd.apparmor.d//&*,` and `ptrace (trace,tracedby,read,readby) peer=cri-containerd.apparmor.d//&*,`, to the template; this override is those two rules until a k3s carries a containerd that has them.

**Why it is opt-in.** It replaces a security profile, and only a host whose kernel stacks the label needs it. A host with AppArmor off, or that does not stack, is better served by containerd's own profile. A host without AppArmor enabled (`/sys/module/apparmor/parameters/enabled` is not `Y`) is left alone with a message even when the variable is true, so the variable can be set for a group.

**What the role does.** containerd's `LoadDefaultProfile` returns at once when a profile of that name is already loaded, so a profile of the same name on the host wins. The role writes `templates/cri-containerd.apparmor.d.j2` to `/etc/apparmor.d/cri-containerd.apparmor.d` (mode 0644, owned by root through `become`), which `apparmor.service` loads at boot before `k3s-agent` starts, and which therefore survives a reboot. The template is containerd's `v2.1.4-k3s2` profile as it renders on a host whose k3s runs unconfined, plus those two rules and nothing else; the version is recorded in `github_runner_linux_host_containerd_apparmor_containerd_version` and in the file's header. The file is compiled before it replaces the old one (`apparmor_parser --skip-kernel-load --skip-cache`), so a profile the parser rejects never reaches `/etc/apparmor.d`. The role then loads it with `apparmor_parser --replace` when the file changed, and once when the kernel does not list the profile at all (`/sys/kernel/security/apparmor/profiles`). AppArmor applies a replaced profile to the processes already confined by it, so no pod is restarted for the rules to take effect. A second run changes nothing, and under `--check` the install and the load are reported and not made.

**It does not weaken the host.** The profile is containerd's own, with two rules added that let the processes of a container signal and trace each other under the stacked label, which they can already do under the plain one (`peer=cri-containerd.apparmor.d` has the same two rules, and the `ptrace` rule still depends on the kernel's other settings, Yama among them). The denials of `/proc`, `/sys` and `mount` are the same, and nothing is added for the host's processes or for other profiles.

**It is tied to a containerd version.** The profile is a copy of one containerd's template, and containerd stops generating its own once this one is loaded, so a k3s that moves to a newer containerd would silently keep this profile instead of getting the newer template. The role therefore reads which containerd the host's k3s carries and fails, before writing anything, when it is not `github_runner_linux_host_containerd_apparmor_containerd_version`. It reads the linker flags of the binary k3s unpacks on its first start at a release (`<data dir>/data/current/bin/k3s`, where `data/current` is the symlink k3s keeps to it): they name the k3s release (`k3s/pkg/version.Version`) and the containerd it carries (`containerd/v2/version.Version`), and the unpacked binary is the one `k3s-agent` runs. `k3s --version` does not name the containerd, and the `k3s` in `/usr/local/bin` holds the unpacked binary compressed, so neither can be read. The unpacked binary counts only when its release is the release of the `k3s` binary on the host: right after the cluster role has replaced that binary k3s has not unpacked the new one, so the role says the containerd was not checked, and so does a host where k3s is not installed or has not started yet. Run the role again once k3s is running; it refuses then if the new k3s carries another containerd. A binary whose flags do not name its release or its containerd is refused rather than trusted.

**When to remove it.** When a k3s release ships a containerd that contains pull request 14487 (read the `template.go` of its `k3s-io/containerd` tag, which the refusal names), or when the host stops stacking the label. Set the variable to false, which leaves the file where it is, then remove the override on the host so that containerd generates its own again: unload the profile with `apparmor_parser --remove /etc/apparmor.d/cri-containerd.apparmor.d`, delete the file, and restart `k3s-agent`, which loads containerd's own profile on start. To move to another containerd that still needs the rules, regenerate the template from its `template.go` with the rules of the pull request, and change the version variable with it.

For the fleet, set it in the `host_vars` of each Ubuntu 26.04 native node.

## Limiting the battery's charge

`github_runner_linux_host_battery_charge_limit: true` keeps the battery from charging past `github_runner_linux_host_battery_charge_limit_percent` (80 by default, 1 to 100), which wears a lithium cell less than sitting at full charge on mains power all day does. The role writes the percentage to `/sys/class/power_supply/<battery>/charge_control_end_threshold` now (`github_runner_linux_host_battery_device`, `BAT0` by default), and installs a systemd oneshot unit, `github-runner-battery-charge-limit.service`, that writes it at every boot, since the attribute does not survive a reboot. The unit is ordered after `systemd-udev-trigger.service`, which coldplugs the devices, and has `ConditionPathExists` on the attribute, so a host without it skips the unit instead of failing; power supplies carry no systemd device unit to order after. A host whose battery has no such file (no battery, or firmware that does not offer the limit) is skipped, and the run says so.

## Running without a desktop

`github_runner_linux_host_headless: true` sets the default target to `multi-user.target` and stops and disables the display manager. A desktop session has an idle suspend of its own, independent of logind and of the lid, so it can suspend a host that `github_runner_linux_host_keep_awake` has made ignore its lid, and it holds memory a node can use. Stopping the display manager ends the desktop session.

Which unit the display manager is gets worked out from the host, because the alias `display-manager.service` is not a reliable name for it: disabling the alias removes its link, after which it is not loaded and `systemctl stop` on it exits 5, and a release can load only the display manager's own unit (Ubuntu 26.04 LTS has `gdm.service` loaded and `display-manager.service` not). The resolution order is:

1. `github_runner_linux_host_display_manager_unit`, when set, is the display manager, used as it is; nothing else is read. It is stopped if it is active and disabled if it is enabled.
2. Otherwise each unit of `github_runner_linux_host_display_manager_candidates` is read in order (`display-manager.service`, `gdm.service`, `gdm3.service`, `lightdm.service`, `sddm.service` by default), an alias reading as the unit it resolves to. The first that is loaded and active is the display manager.
3. If none is active, the first that is loaded and enabled is, which is a display manager an earlier run stopped and left enabled; it is disabled.
4. If none is loaded and active or enabled, the host has no display manager to stop, the role says so and does not fail.

The display manager is stopped before it is disabled, so a name that is an alias is still loaded when it is stopped. Under `--check` each change is reported and none is made. The step that disables the services a node does not need is not affected: `github_runner_linux_host_unneeded_services` names real units, each read by its own name, and a unit the host does not have is left alone.

## Disabling services a node does not need

`github_runner_linux_host_disable_unneeded_services: true` disables the units in `github_runner_linux_host_unneeded_services` that are enabled, and stops those that are running: `cups.socket`, `cups.path`, `cups.service`, `cups-browsed.service`, `bluetooth.service` and `ModemManager.service` by default. A dedicated node needs none of them, and each is a daemon and an attack surface that runs for nothing. The socket and path units come first, so they stop before the service they would start again. `avahi-daemon`, which gives a laptop the `.local` name it is reached by, and NetworkManager are not in the list. A unit the host does not have is left alone.

## Security updates that never reboot the host

`github_runner_linux_host_unattended_upgrades: true` installs `unattended-upgrades` and writes `/etc/apt/apt.conf.d/52github-runner-unattended-upgrades`, which refreshes the package lists and installs updates daily, makes sure the distribution's security pocket is among the allowed origins, and sets `Unattended-Upgrade::Automatic-Reboot` to `false`: a node must not reboot itself, and a reboot that an update needs is for the upgrade below, or for whoever has drained the node. The file's name sorts after Ubuntu's `20auto-upgrades` and `50unattended-upgrades`, so its values win; the distribution's own configuration may allow other origins as well. Debian and Ubuntu only.

## Upgrading on demand

`github_runner_linux_host_upgrade: true` is for the one run that upgrades the host, never part of every run, so a fleet leaves it false in `host_vars` and sets it with `-e` for that run. It runs `apt-get update` and `apt-get dist-upgrade`, reboots the host if `/var/run/reboot-required` says the upgrade needs one (`ansible.builtin.reboot`, which waits for a new boot and for `multi-user.target`; the run then fails if the reboot is still due, naming the kernel before and after), and then `apt-get autoremove --purge`. The autoremove comes after the reboot because it can only remove the kernels the upgrade superseded once the new one is the running kernel. Under `--check` it runs both apt-get steps with `--simulate`, skips the update, and reports whether it would reboot.

The reboot is guarded. A host on which any unit of `github_runner_linux_host_node_services` (`k3s-agent.service` and `k3s.service` by default; a Docker node would list `docker.service`) is active is a running node of the cluster, and rebooting it takes the node off the cluster and fails the jobs its runner pods are running. The role refuses: it fails, after the packages are upgraded and before any reboot or autoremove, naming the active unit. Draining the node and stopping its service is the operator's, and a run with `github_runner_linux_host_upgrade_reboot_running_node: true` reboots it anyway. `github_runner_linux_host_upgrade_reboot: false` installs the upgrade, says a reboot is due, and reboots nothing. A release upgrade (`do-release-upgrade`) is not part of this.

## Keeping Tailscale current

`github_runner_linux_host_tailscale_update` (default `true`) is the one step that is on by default, because it installs nothing and changes only what the host already runs. When the package `tailscale` is installed and apt has a newer release of it, the role upgrades that package alone (`apt-get install --only-upgrade tailscale`, never a blanket upgrade; the index is refreshed first with `apt-get update`), and it enables and starts the `tailscaled` service if either is missing (`systemctl enable --now tailscaled`). Tailscale's own package scripts restart a running `tailscaled` on upgrade and keep its login, and its apt repository is where newer releases come from ([Install Tailscale on Linux](https://tailscale.com/kb/1031/install-linux)); the restart drops the host\'s tailnet connections, an SSH session over it included, for a moment. The role never installs the package, adds the repository, joins a tailnet or logs in.

A host that is not Debian or Ubuntu, a host without the package, and a package no repository carries a newer release of are skipped, with a message and without failing the run. A native node of the cluster (`github_runner_cluster_node_mode: native` while `github_runner_cluster_native_tailscale_install` is true, its default) is skipped too: the cluster role installs the release it pins there, `github_runner_cluster_tailscale_version`, and puts a host back to it on every run, so a newer release put here would be replaced on the same run. Under `--check` each change is reported and none is made.

## Variables

- `github_runner_linux_host_keep_awake` (default `false`): mask the sleep targets and have logind ignore the lid switch.
- `github_runner_linux_host_networkmanager_connectivity_check_off` (default `null`): `null` leaves connectivity configuration unmanaged; either boolean fails because this feature is not ready.
- `github_runner_linux_host_networkmanager_connectivity_dropin`: where the connectivity drop-in goes, a variable for tests, not a setting.
- `github_runner_linux_host_wifi_powersave_off` (default `false`): turn Wi-Fi power save off, in NetworkManager or, on a host without it that runs systemd-networkd, with a udev rule and a unit that run `iw`, and on the radio.
- `github_runner_linux_host_k3s_prerequisites` (default `false`): load the modules and set the sysctls k3s needs, now and at boot.
- `github_runner_linux_host_containerd_apparmor_stacking_fix` (default `false`): install and load the AppArmor profile for containerd's containers that allows signals and ptrace between peers of a stacked label, on a host with AppArmor, and refuse a k3s whose containerd it was not taken from.
- `github_runner_linux_host_battery_charge_limit` (default `false`), `github_runner_linux_host_battery_charge_limit_percent` (default 80) and `github_runner_linux_host_battery_device` (default `BAT0`): limit the battery's charge, to what, and which battery.
- `github_runner_linux_host_headless` (default `false`): boot to `multi-user.target` and stop and disable the display manager.
- `github_runner_linux_host_display_manager_unit` (default empty) and `github_runner_linux_host_display_manager_candidates`: the display manager's unit when the host names it, and otherwise the units tried in order to find it (see Running without a desktop).
- `github_runner_linux_host_disable_unneeded_services` (default `false`) and `github_runner_linux_host_unneeded_services`: disable and stop the listed units.
- `github_runner_linux_host_unattended_upgrades` (default `false`): install and configure unattended-upgrades for security updates, never rebooting.
- `github_runner_linux_host_upgrade` (default `false`): upgrade the packages, reboot if due, and autoremove, for one run.
- `github_runner_linux_host_upgrade_reboot` (default `true`), `github_runner_linux_host_upgrade_reboot_running_node` (default `false`), `github_runner_linux_host_node_services` and `github_runner_linux_host_reboot_timeout` (default 600): whether the upgrade reboots, whether it may reboot a running node, which units make a host a running node, and how long it waits for the host to come back.
- `github_runner_linux_host_sleep_targets`, `github_runner_linux_host_lid_switch_settings`, `github_runner_linux_host_kernel_modules`, `github_runner_linux_host_sysctl_settings` and `github_runner_linux_host_default_target`: the targets masked, the logind settings set to `ignore`, the modules loaded, the sysctls set and the target booted to. Constants, not settings; variables only so the tests can narrow them.
- `github_runner_linux_host_containerd_apparmor_containerd_version`, `github_runner_linux_host_containerd_apparmor_profile_name`, `github_runner_linux_host_containerd_apparmor_profile_file`, `github_runner_linux_host_apparmor_enabled_file`, `github_runner_linux_host_apparmor_profiles_file`, `github_runner_linux_host_k3s_binary` and `github_runner_linux_host_k3s_data_dir`: the containerd version the profile was taken from, the profile's name and file, what the role reads of the kernel's AppArmor, and the k3s binary and data directory it reads the containerd from. Not settings; variables only so the tests can point them at a stand-in (the version changes only together with the template).
- `github_runner_linux_host_logind_dropin`, `github_runner_linux_host_networkmanager_dropin`, `github_runner_linux_host_sysfs_net_dir`, `github_runner_linux_host_wifi_udev_rule`, `github_runner_linux_host_wifi_powersave_unit`, `github_runner_linux_host_modules_load_file`, `github_runner_linux_host_sysctl_file`, `github_runner_linux_host_sys_module_dir`, `github_runner_linux_host_power_supply_dir`, `github_runner_linux_host_battery_unit`, `github_runner_linux_host_unattended_upgrades_file`, `github_runner_linux_host_reboot_required_file`: where the role's files go and what it reads and runs. Not settings; variables only so the tests can point them at a stand-in.
- `github_runner_linux_host_tailscale_update` (default `true`): keep the installed Tailscale package current and its service running, as under Keeping Tailscale current above.

## Tests

`tests/unit/test_linux_host.py` runs the role (`tests/linux_host/run.yml`) against stand-ins for `systemctl`, `nmcli`, `iw`, `udevadm`, `modprobe`, `sysctl`, `apt-get`, `dpkg-query`, `uname` and `shutdown` on `PATH`, with every file the role writes or reads redirected and the host's facts stood in for. It checks for each step but the Tailscale update that it is off by default (and that the update is on, and leaves the host alone without the package), does what it says, changes nothing on a second run, and under `--check` reports each change and makes none; and in particular the order of the modules and the sysctls, a battery without the attribute, a limit outside 1 to 100, a display manager worked out from the alias, from its own unit when the alias is not loaded and from a unit the host names, a host with none, services the host does not have, the apt steps refused on a host without apt, the order of the upgrade, a running node's reboot refused with the packages already upgraded, and the defaults, argument specs and this README agreeing.
