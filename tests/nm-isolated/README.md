# Isolated NetworkManager fixture

This source-only fixture is incomplete. Its preflight, private bus launcher, PolicyKit stub and non-root Update2 client are components for a disposable VM harness, not evidence of isolation or a passing integration test. Nothing orchestrates a real NetworkManager daemon yet.

Use only a disposable Linux VM whose system bus, network devices, filesystem and credentials are disposable. The VM must be independently verified before creating `/run/nm-isolated-test/disposable-vm`; this sentinel is an assertion by the operator, not proof of isolation. The fixture refuses to proceed without the sentinel and `systemd-detect-virt --vm`. Neither check makes an existing VM safe. Do not run on a host carrying real workloads or credentials.

Dependencies for the intended harness are NetworkManager 1.54.3, systemd-detect-virt, a private D-Bus system bus, Python 3 with PyGObject and a non-root test account. The test bus must be isolated from the host system bus and the VM must contain only disposable NetworkManager state and profiles. NetworkManager's keyfile storage and runtime directories require VM-level isolation; changing only `--state-file` is not sufficient.

The PolicyKit stub accepts an explicit bus address under `/run/nm-isolated-test/`, holds non-root authorisation requests and exposes test control methods to release them. The path check does not prove the bus is private: the disposable VM operator must ensure it is a dedicated test bus and not a link to another bus. NetworkManager authorises root directly, so Update2 must come from a non-root client. No-fence must prove a delayed update can complete after that client disconnects; fence must perform a confirmed identical Update2 from a separate client before releasing the delayed request and prove the old version is rejected. Restart must check the NetworkManager unique bus owner and profile version before and after daemon replacement. `scenarios.py` expresses those assertions against an injected adapter, and `scenario_bus.py` supplies bounded D-Bus profile and owner reads with a stable-version check. `ScenarioAdapter` composes injected held-client, separate-writer, authority, outcome-observer and daemon-restart ports under one deadline. `lifecycle_ports.py` connects child-process and PolicyKit control interfaces, `client_launcher.py` supplies a non-root child launcher using the fail-closed isolation guard and fixed private bus address, but it has not been exercised with real processes and there is no end-to-end integration. Restart explicitly reports inconclusive. `FixtureOwner` claims a control object within one Python process and tears down the injected authority and bus children on retirement; it does not establish exclusive ownership across different D-Bus proxy objects or processes. A disconnected client's reply cannot establish the delayed request's outcome. `OutcomeObserver` compares snapshots only after an injected request-specific daemon-completion barrier, reporting applied, not-applied or inconclusive. `AuditObserver` correlates structured audit records by daemon instance, client PID, profile UUID, operation and a post-submission cursor, distinguishing success and the source's exact version-mismatch reason from missing or ambiguous events in the observed batch. It returns as soon as one matching batch arrives, so it relies on the dedicated client submitting exactly one update; it cannot detect a later duplicate. `audit_log.py` parses NetworkManager 1.54.3 log-format fields from a caller-supplied binary capture and tracks complete lines with byte cursors; its input must be an exclusive, append-only capture for the named daemon. `AuditScenarioObserver` marks the capture before submission and binds its cursor to the held request. The daemon lifecycle now requests INFO logging and drains its merged output into a bounded capture with an audit-reader adapter; overflow makes observation fail rather than discarding evidence. No real-daemon output or live format validation exists; a PolicyKit release alone is not a completion barrier, and an unchanged profile does not prove a version-mismatch rejection. It also requires exclusive writers. Restart records profile versions on either side without assuming versions survive daemon replacement.

The client reads a profile's settings and version, then sends an in-memory Update2 with a `version-id` fence; `--unfenced` explicitly omits the version for the control case. After a request is held, the PolicyKit control method `AllowLater(true)` allows subsequent non-root requests without releasing the held request, so a separate fence writer can finish first. This mode allows all subsequent valid non-root requests and therefore requires exclusive fixture use. `--metric` changes its IPv4 route metric; omitting it sends identical settings. By default the client waits for the daemon's reply. With `--disconnect-after-held`, it submits asynchronously and uses a separate bus connection to wait for the stub to report one new held request before disconnecting, printing its cancellation id for the controller. This mode requires an empty authority queue and an exclusive fixture, so another client's authorisation cannot be mistaken for its own; it fails on a timeout or ambiguous queue. The client enforces the non-root, VM and sentinel checks before connecting to an explicitly addressed test bus. As with the stub, the address check does not establish that the bus is private. Run its offline request-construction tests with `python3 -m unittest discover -s tests/nm-isolated -p 'test_*.py'` from the repository root.

`guest_transport.py` supplies a bounded JSON-lines request/response codec and fixed-handler dispatch for an injected binary stream. Its `DeadlineStream` bounds socket I/O by a single monotonic deadline, and its `ready` handler reports that dispatch is responsive, not that the guest is isolated or NetworkManager is ready. The QEMU command defines a virtio serial port and private Unix socket, and `guest_agent.py` can serve one readiness request on the named guest port with a deadline. `host_transport.connect_ready` retries the workspace socket within a single deadline and requires a matching readiness reply while the QEMU child remains alive. An injected guest runner can handle a validated scenario request, and `vm_factory.request_scenario` sends one bounded request over the ready socket. The agent entrypoint wires `guest_runner` to the scenario functions. `guest_owner` composes injected bus, authority, daemon, profile and adapter contexts with reverse-order cleanup, with default private-bus, PolicyKit process and NetworkManager factories. The authority factory probes its private-bus control method, and the profile factory creates and deletes an unsaved test profile. The scenario-adapter factory composes the existing ports, but the production isolation guard deliberately refuses, so this is not a runnable real-daemon scenario path. `guest_manifest.json` specifies the prebuilt Debian guest's packages and fixture files; `guest_provision.py` validates their presence and the NetworkManager version without installing or starting anything. An installation function checks fixture bytes against caller-supplied trusted digests and validates installed packages before copying, but production provisioning has no authorised entry point: the provenance guard refuses and no trusted digest distribution exists. It does not configure a bus or PolicyKit, build an image, verify package contents or prove guest isolation. There is no real QEMU test.

`VMScenarioOwner` composes injected VM and connection contexts with fresh-identity tracking and bounded retry attempts; `vm_factory.make_owner` connects it to the QEMU context and readiness socket; its deadline depends on the underlying operations honouring their timeouts, and it returns a socket rather than a complete scenario adapter. `qemu_vm.disposable_vm()` is source-only host-side lifecycle scaffolding: it creates a named qcow2 overlay and constructs a QEMU command without network devices or host shares, verifies the child executable and argument vector through Linux procfs, and reaps it. It requires a trusted qcow2 base image and private workspace; it checks qemu-img JSON for a standalone qcow2 with no backing or external data file, requires an owned read-only base and an owned private workspace, but does not provide guest provisioning, readiness or a test transport. These checks assume the image and its parent directories cannot be replaced concurrently; mode bits do not make an owned image immutable. It has not been run with QEMU. A guest cannot prove its host is disposable, and the guest-side isolation verifier remains fail-closed.

`private_bus.private_bus()` starts a foreground `dbus-daemon` with an explicit private socket under `/run/nm-isolated-test/`, after the VM and sentinel checks, and terminates and reaps the child on exit. `networkmanager.networkmanager()` composes that bus with the daemon's lifecycle and sets its system bus address explicitly, but its production filesystem isolation verifier always refuses to start: it checks the VM guard, Linux mount namespace and mount table, but cannot establish mount provenance or exclude namespace escape from that evidence alone. Its injectable verifier is exclusively for offline tests, not authorisation to run a daemon. The bus launcher uses `bus.conf`, which names the non-root `nm-isolated` account, and waits for an explicit-address D-Bus Ping before yielding. The account must exist in the guest. Neither the policy nor readiness has been tested against a real bus. The preflight still exits non-zero and must not be interpreted as a successful integration run.
